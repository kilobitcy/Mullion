# ADR-010: 隧道是一等对象,并独占一条 SSH 连接

- 状态: 已接受
- 日期: 2026-08-11
- 关联: spec F110~F117、设计文档 `docs/superpowers/specs/2026-08-11-tunnels-design.md`(D1)、
  切片 T-a(数据层 + 配置 UI,已完工)、ADR-009(一条连接多 channel)、ADR-006(store crate)

## 背景

F110~F117 要做 SSH 端口转发(`-L` / `-R` / `-D`)。参考对象是 PuTTY 的「转移规则」
对话框——那里隧道是**会话的一个配置分节**:打开会话即建立转发,关闭会话即断开。

抄这个模型有两个东西要先定下来,而它们分别撞上了本项目的既有约定:

1. 隧道**归属**谁?PuTTY 说归会话。
2. 隧道的字节走**哪条连接**?ADR-009 刚刚定过「一条 SSH 连接承载多个单元」,并明确
   否决了「每单元一条 TCP + 一次认证」。

## 决策

**隧道是与会话平级的一等对象,持有一个 `session_id` 引用会话的拨号参数;
每条隧道启动时用那些参数走 `establish()` 另开一条自己的 SSH 连接。**

```
会话 web-01(已连)                隧道 #1(引用 web-01)
  └─ Arc<Handle> A                 └─ SshConnection B   ← 另一条 TCP
       ├─ pane 1 (PTY)                  └─ direct-tcpip
       └─ pane 2 (PTY)
```

存储上落在同一个 `sessions.toml` 的 `[[tunnel]]` 数组(schema v7),不是会话记录的子表。
引用是**纯引用、不覆盖**:隧道不能「用 web-01 的地址但换个用户名」,要换身份就另建会话。

## 备选与否决理由

### 备选 A:抄 PuTTY,隧道作为会话的子配置

否掉。本项目最常见的隧道用途是「把远端 3306 转发到本地给 DBeaver 用」,这件事
**不需要开终端窗口**。做成会话子配置意味着:要转发就得先连一个自己不看的 PTY,
关掉那个窗口转发就没了。这不是实现难度问题,是这个模型表达不了这个需求。

一等对象的代价是引用会悬垂(会话被删),这个代价被明确接受并做了处理(见后果 2)。

### 备选 B:复用会话已有的那条连接,在上面开 `direct-tcpip` channel

这是「和 ADR-009 保持一致」的那个选项。否掉,两条理由,第二条是硬的:

1. **ADR-009 的推理针对 pane,不能平移到隧道。** 那条推理的前提是「单元数量随分屏
   增长、用户会频繁开关,每次都付一次完整建链(高延迟链路上几百 ms 到几秒,外加一次
   TOFU 弹窗)不可接受」。隧道的数量级和生命周期完全不同:手动启停、长期驻留、
   通常个位数。为一条要挂几个小时的隧道付一次建链是划算的。

2. **`-R` 在这个方案下编译不过。** 核实过 `russh 0.54.5` 的实际签名
   (`~/.cargo/registry/src/*/russh-0.54.5/src/client/mod.rs`):

   | 方法 | 行 | 接收者 |
   |---|---|---|
   | `channel_open_direct_tcpip`(`-L` / `-D` 用) | 649 | `&self` |
   | `tcpip_forward`(`-R` 用) | 696 | **`&mut self`** |
   | `cancel_tcpip_forward` | 722 | `&self` |

   ADR-009 决定了会话的 handle 以 `Arc<Handle<ClientHandler>>` 在多个 pane 之间共享,
   而 `Arc` 给不出 `&mut`。也就是说:**只要沿用 ADR-009 的共享方式,`-R` 就没有
   可用的入口**。隧道独占自己的 `SshConnection` 才拿得到可变借用。

   (这三个接收者并不对称——`cancel_tcpip_forward` 是 `&self`。别据此推断
   「russh 的转发 API 都不要 `&mut`」,写代码前按 API 漂移的规矩重查当前锁定版本。)

### 备选 C:一等对象,但所有隧道共用一条到同一主机的连接(按 host 池化)

否掉,理由是复杂度不换来东西。要池化就要处理引用计数、最后一条隧道停止时谁来关连接、
以及一条池化连接断掉时 N 条隧道的联动状态。而备选 B 的第 2 条理由在这里同样成立
(池化的 handle 还是共享的,`-R` 还是拿不到 `&mut`)。个位数的隧道省不出这个复杂度。

## 后果与由此引入的约束

1. **建链逻辑不重写。** 隧道拨号 = 用被引用会话的参数构造 `SshConfig` 后调
   `session.rs::establish(cfg, policy)`——代理 → 跳板链 → 握手 → 指纹 → 认证整条链路
   已经在里面。任何「隧道专用的简化拨号」都是错的:它会绕过跳板和 TOFU。

2. **引用会悬垂,而悬垂必须说出来,绝不静默改指向。** 删会话前的确认框列出会失去引用
   的隧道(超过 5 条说「另有 N 条」);已悬垂的隧道在编辑器里**保持原 `session_id`**
   并显示「⚠ 已删除的会话 (id=N)」。静默跳到第一条会话 = 把转发悄悄接到另一台机器上,
   这是本功能最危险的一种失效。守护测试见
   `store::tunnel::tests::dangling_tunnel_reference_is_rejected_never_silently_dropped`、
   `ui::session_manager::tunnel_ui_tests::a_dangling_tunnel_says_so_instead_of_snapping_to_another_session`。

3. **每次启动隧道都是一次完整建链,可能需要交互**(TOFU 确认 / 输密码 / 输私钥口令)。
   由此推出 D6「纯手动启停」:开机自动拨 N 条 = 并发糊一屏模态框,在高延迟代理链路下
   还会全部超时。`autostart` 字段在 schema 里留了位置,但 T-a 没有 UI 也没有行为。

4. **重连策略与 ADR-009 不同,且这不是矛盾。** ADR-009 说「不做 per-unit 重连」,
   因为 pane 断了重连回来是空 shell——滚动内容和正在跑的 TUI 都没了,语义不等价。
   隧道是**无状态**的:重连后转发语义完全等价,用户侧唯一感知是那一瞬间的 TCP 断了。
   所以隧道做有界指数退避(1s→2s→4s…封顶 30s,连续 8 次后停下标红等人工),
   但受两条硬约束:**需要交互的凭据不自动重连**(不后台反复弹窗),
   **指纹变更立即停止绝不重试**(可能是中间人,自动重连等于自动把凭据送过去)。

5. **依赖方向不变。** `mullion-ssh` 仍然不认识「隧道」这个概念:`TcpListener` 与
   SOCKS5 服务端放在 `mullion-ssh`,吃的是地址和字节流;哪条规则、引用哪个会话、
   界面上怎么显示,全部留在 `mullion-app`。`mullion-store` 只存记录,零 async。

6. **绑定安全是类型层面的,不是 UI 纪律。** `TunnelKind` 是带数据枚举,`Dynamic`
   分支**不存在** `target_*` / `expose` 字段——「`-D` 锁死 loopback」因此没有
   可写错的地方。`-L` / `-R` 的 `expose: bool` 默认 `false`,方向选成
   「暴露要显式打开」而不是 `local_only`,是因为 serde 对缺字段的 bool 默认给 `false`,
   而 `false` 必须落在安全那一侧。

7. **`-R` 的远端绑定不可验证。** 远端 sshd 的 `GatewayPorts` 决定 `-R` 到底绑在
   loopback 还是 `0.0.0.0`,协议不回报这件事。UI 只能明写「实际绑定由远端 sshd 决定」,
   不能假装自己知道。

## 现状

T-a 已落地数据层(`mullion-store` 的 `tunnel.rs`、schema v7)与配置 UI
(会话管理器的「会话 / 隧道」模式条、隧道列表、隧道编辑器)。**转发本身还没实现**,
每行的「启动」按钮是真禁用态(`ui.disable()`,不是画成灰的)。本 ADR 描述的连接模型
将在 T-b 兑现;在那之前,上面第 3、4、7 条还没有对应代码。
