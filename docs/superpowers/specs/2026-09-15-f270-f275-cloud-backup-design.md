# F270~F275 云端备份 设计文档

> 产出自 2026-09-15 的 grilling 会话。**决策全部由用户拍板**，本文只记录决策与理由。
> 实现计划见 `docs/superpowers/plans/2026-09-15-f270-f273-cloud-backup-upload.md`（片一）。

## 0. 一句话

把 F46-a 的整机迁移包，用主密码派生的密钥整体加密之后，推到**用户自己的** S3 兼容
对象存储上；任一台机器都能推、都能拉，冲突由用户显式仲裁，绝不自动合并。

---

## 1. 与 spec 非目标的关系（N-G4 要改写）

`spec.md` 原文：

```
- N-G4 云同步、账号体系。配置就是本地文件。
```

改写为：

```
- N-G4 **账号体系**。不做 Mullion 自己的用户账号 / 登录 / 服务端。云端备份（F270~F275）
  用的是**用户自己的**对象存储、用户自己的 AK/SK —— 我们不运营任何服务端、不持有任何
  用户数据。**本地文件仍是唯一真值源**，云只是传输与仲裁介质（整包 LWW，云端没有权威性）。
```

后半句能留，是因为选的是**整包 last-writer-wins + 显式仲裁**而不是记录级合并：
云上那份从来不参与「哪条记录更新」的裁决，它只是一个带版本号的副本。

---

## 2. 为什么不做记录级合并

四条硬事实，任何一条单独就足以否掉自动合并：

| # | 事实 | 后果 |
|---|---|---|
| 1 | 时间戳只有 `SessionRecord.modified_at`。`GroupRecord` / `CredentialRecord` / `TunnelRecord` **一个时间戳都没有**，`ProjectRecord` 只有 `created_at` / `last_accessed_at`（不是编辑时间） | 记录级合并需要的「谁更新」在四类实体上答不出来 |
| 2 | 没有删除墓碑 | 「对方删了这条」与「对方还没有这条」长得一模一样 → 删掉的会话会自己长回来（本项目反复踩的「静默复活」形状） |
| 3 | id = `max+1`（`vault.rs:475`） | 两台机离线各建一条 → 都是 id=7。而 id 是 `secrets.enc` 的键、`TunnelRecord.session_id`、`ProjectRecord.nodes`、`layouts/*.toml` 的引用键 —— 撞车不是「合并成一条」，是**引用图整个错位**（A 机的隧道挂到 B 机的会话上），零报错 |
| 4 | 写盘全是整份覆盖（F247/F248 已登记的缺陷族） | 半新半旧的中间态没有任何一层挡得住 |

补齐这四条 = schema v13→v14 大迁移 + 一整个 merge 引擎，工作量 3~5 倍。**不做。**

## 3. 决策表

| # | 决策 | 理由 / 代价 |
|---|---|---|
| D1 | 语义 = 双向同步，但**整包 LWW + 显式仲裁**，绝不自动合并 | 见 §2。代价：并发编辑必丢一边，靠 `backup-<时间戳>/` 兜底 |
| D2 | 后端 = **S3 兼容**（通吃 OSS / R2 / MinIO / COS），不绑死阿里云 | 一份 SigV4 代码的成本与「只做阿里云」一样，不把自己锁死在一家 |
| D3 | 新建 **`mullion-cloud`** crate | 现有五个 crate 没有合法住处：`store` 是「零 async、仅同步 IO、可纯单测」，`ssh` 是「只认字节流、不认识 pane」，塞 HTTP 进任一个都是品类错误；塞 `app` 则落在「最难测」那层（F253~F256 刚踩过「App 的方法测不了 → 交付判据整体恒绿」）。架构表五条变六条，**要写 ADR** |
| D4 | HTTP = **ureq 3**，`default-features = false`，显式挑 `rustls`(ring) + `socks-proxy` | ureq 3 默认就用 rustls + **ring** provider，正是 ADR-005 为交叉编译干净而选的后端。⚠️ 官方文档原话「does not guarantee defaulting to it indefinitely」→ **provider 必须在 Cargo.toml 里钉死**，静默切到 aws-lc-rs 会让交叉编译炸，且只有交叉编译时才暴露。不开 gzip（会再拉一条 `flate2` 路径，而 `RUSTSEC-2026-0153` 对本项目真可达）。阻塞式 → `mullion-cloud` 也是零 async，与 `store` 同气质 |
| D5 | 载荷 = **整包用 `Vault` 已持有的 `key` 整体加密**，外层套 `secrets_file::encode` 同款文件头（salt + params） | `Vault` **不保留主密码明文**（只有 `key: [u8;32]` + `scheme`），所以「上传时用主密码重封」需要 app 常驻主密码明文 —— 新攻击面、新生命周期。用 `key` 直接封：零常驻密码、零额外 KDF。且 `sessions.toml` 里的真机 IP / 用户名 / 跳板拓扑不落云端明文（F46-a 的本地包是 base64 明文，那是用户自己保管的文件，云端是第三方存储，口径不该照搬） |
| D6 | **前提：必须已设主密码（F71）** | 钥匙串方案下 `key` 来自本机钥匙串，封出来的东西换台机器解不开 —— 云备份的主场景「换新电脑」当场失效。未设时设置页那一节整节灰掉 + 引导跳到「安全」分节 |
| D7 | 包的范围 = `sessions.toml` + `settings.toml` + `known_hosts.toml` + `secrets.enc`，**不带 `layouts/`** | 窗口几何 / 分屏树是**本机属性**（分辨率、屏数），推到另一台机覆盖它的现场是错的；且它是配置目录里变动最频繁的东西，带上等于让「内容变了」近似恒真。**`install` 对 `layouts/` 本来就是合并写入而非整份替换**（F46-a 事实④），所以不带 = 不动目标机现场，天然安全，不需要任何新开关。`known_hosts.toml` 反过来要带：跨机共享是收益（新机不用重新 TOFU 一遍） |
| D8 | 对象布局 = **追加式序号对象** `<prefix>/<6位序号>-<UTC时间>.mpk`，`ForbidOverwrite=true`；「最新」= List 后序号最大那条 | **OSS 的 `PutObject` 没有 `If-Match`**（只有 `ForbidOverwrite`），S3/R2 才有条件写 —— 选了「通吃」就得按最小公分母设计，不能依赖 CAS。追加式天然有历史版本，顺手把 spec F46 的「自动备份保留 N 份」做了；两台机同时推只会产生两个相邻序号，一条都不丢 |
| D9 | 触发 = 菜单「立刻备份到云」永远可用 + 每 N 分钟（默认 30）算一次**内容指纹**，变了才真的 PUT。**退出时不做网络 IO** | Mullion 是长时间开着的（连着远端 tmux 跑 Claude Code），退出很少发生 → 「退出时推」几乎等于不推，而在关闭路径上做几秒网络 IO 会被当成卡死。判据必须是内容指纹（sha256）而不是列举式脏标记 —— 「列举式门控在加档时必然漏」已经踩过三次，漏一次的后果是「用户以为备份了其实没有」 |
| D10 | 仲裁 = 状态栏非模态提示 + 云端弹窗；**绝不抢焦点**；未仲裁前定时上传**暂停**且状态栏显示「已暂停」 | 终端里正跑着 Claude Code，模态框抢键盘焦点与 T8/F199 一路修过来的方向相反。暂停是必须的（否则会把别人的改动洗掉），但暂停必须**可见**，否则又是一个静默失效 |
| D11 | 云配置住**单独的 `cloud.toml`**，**不在 `TOP_LEVEL_FILES` 白名单里** | 若 AK/SK 进 `secrets.enc`：① 拉一份云端配置下来会把本机 AK/SK 覆盖成云端那份的，两台机用不同 RAM 子账号就串了；② 云端那份若是几个月前推的、AK 已轮换，拉下来本机拿到过期密钥 —— 之后永远推不上去，报 `403`，与「配置被覆盖」毫无关联，排查极难。endpoint/bucket/游标同理，都是「本机对云的看法」，不该被云端内容覆盖。不在白名单 → `install` 天然碰不到它 |
| D12 | AK/SK 用 vault key 加密后内嵌 `cloud.toml`；`set_master_password` / `clear_master_password` **必须连带重封 `cloud.toml`** | 不重封的话，改一次主密码 AK/SK 当场解不开，云备份静默失效，错误在几十分钟后的一次定时上传里才出现。**这是接线，不是选项。** `clear_master_password` 退回钥匙串方案后云端包不再可跨机 → 等于云备份前提消失，要显式告知并关掉开关 |
| D13 | 改主密码后：云端旧包**保留并标注**为「需要旧主密码」，可当场输旧密码试解；改密码成功后**立刻推一份新的**，不等定时 | 删不可逆，而改密码的理由往往是「怕泄了」，那时候旧备份更不该丢。「立刻推」是因为：不推的话，一台新机在这段窗口里拉下来的全是解不开的 |
| D14 | 清理 = 推完新份后删到只剩 N 份，但**跳过 salt 与当前不同的那几份**（包头不解密就能读出 salt/params），它们单独保留最近 1 份。删除失败只记日志，不算备份失败 | 无脑按序号删最旧的，会把 D13 保留下来的异密码份**先删掉**（它们最旧），等于把 D13 作废 |
| D15 | 切片 = **先上传后拉取**。片一（F270~F273）= cloud crate + ADR + 配置分节 + 手动/定时上传 + 状态栏 + 主密码接线，**发版真机验**；片二（F274/F275）= 拉取 + 云端弹窗 + 仲裁 + 清理 | SigV4 签名对不对、rustls 在 `x86_64-pc-windows-gnu` 交叉编译后能否真握手、SOCKS 代理链路通不通、exe 体积增量 —— 四样全在 CLAUDE.md「你无法验证的东西」里，越晚暴露越贵。且「只上传」本身已是完整可用的灾备功能 |

## 5. 架构不变量的增补（ADR 要写的那条）

```
mullion-cloud    对象存储客户端。只认「字节 + 键名 + 版本」，不认识 Pack/Session/UI。
                 零 async（ureq 阻塞式）、零 GPU。可对着假 HTTP server 纯单测。
```

依赖方向仍严格单向：`app → {core, term, ssh, store, cloud}`，`cloud` 不依赖其余任何一个。

**`cloud` 不认识 `Pack`** 这条是硬的：打包 / 加密 / 指纹全在 `store`，`cloud` 只收
`&[u8]` 和一个 key 字符串。违反了，「签名算错了」和「包组装错了」就再也分不开。

## 6. 测试策略

三层，缺一层就有一整类错误没人看着：

1. **SigV4 用 AWS 官方测试向量做纯函数单测。** 这是唯一能证明签名对的手段 ——
   假 server 不验签，真 server 只会回一个 `403`（而 `403` 也可能是权限配错）。
2. **协议流程对着本地假 HTTP server 测**（照抄 `mullion-ssh` 的「假 sshd + 拿自家
   客户端打自家服务端」手法）：`ForbidOverwrite` 冲突、List 分页、超时、重试退避。
3. **对真 bucket 的端到端走 `MULLION_LIVE` 式 `#[ignore]` 测试**，AK/SK 从 env 传，
   **绝不写死进库**（同 `mullion-ssh --test live`）。

## 7. 已知代价与待人工验证

**代价：**
- 依赖树：+ureq/rustls/webpki-roots（ring 已在树里，不新增）。当前 605 个 crate。
- exe 体积：刚从 38.6 压到 17.2 MiB，加 TLS 栈之后必须重新量，超过 N6 的 25MB 要报警。

**只有真机能验（片一发版后的人工验收清单）：**
- [ ] `x86_64-pc-windows-gnu` 交叉编译后，rustls 能否真的完成 TLS 握手
- [ ] SOCKS5 代理链路下的实际吞吐与超时
- [ ] 真实阿里云 OSS 对 SigV4 的接受度（V4 兼容细节无一手文档，靠 live 测试证）
- [ ] 加了 ureq 之后的 exe 体积增量
- [ ] 断网 / AK 过期 / bucket 403 三种失败下，状态栏是否真的报出来而不是静默

**顺带的运维建议（写进文档，不是代码）：** AK/SK 用 RAM 子账号、只授权单 bucket 单
prefix，不用主账号密钥 —— 那东西泄漏等于整个阿里云账号。
