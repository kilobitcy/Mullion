## 1. 背景与裁剪原则

`docs/session-mng.md` 是一份 Xshell / MobaXterm 风格的**通用** SSH 客户端字段清单。
Mullion 的定位是「Windows 上通过高延迟代理链路操作远端 tmux 里的 Claude Code TUI」，
清单里相当一部分字段服务的是别的产品形态。

**已定原则**：P0~P3 只排服务于主线场景的字段；越界字段不删除也不实现，
统一登记进 **P4 储备区**（写进 `spec.md` 的「已登记未排期」表），
每条注明*为什么现在不做*与*什么条件下重新评估*。边界扩大时从储备区取。

一处澄清：**SFTP 侧栏不属于越界**——`spec.md` 的 `F50~F57` 已为它排期
（`F50~F55` 为 P1，`F56`/`F57` 为 P2；里程碑表 v0.4 的范围是 `F50~F55`）。
越界的只是清单 §10 里的 ZMODEM/XMODEM 与传输模式细节。

## 4. P0 — 数据地基 + 链路打通

一次把 TOML 格式定死，后续四期**只加字段、不改类型**。

### 4.1 继承策略（D7 展开）

`Option<T>` 的整体覆盖语义只对标量成立。列表与复合对象必须在 P0 就拍板，
否则 P2 落地 tags / icon / color 时会被迫改 `resolve` 签名或拆分类型，直接击穿 D3。

**两种策略，各自一个纯函数：**

- `resolve_override<T>(sources) -> T`：按优先级取第一个 `Some`，末位为内置默认。
- `resolve_merge_list<T>(sources) -> Vec<T>`：各级并集去重，顺序为「上游在前」。

**`resolve` 接受有序的 fallback 源序列，而不是焊死「会话 / 分组 / 默认」三层。**
这是为 F64 预留的：环境等级会带来一层隐含默认色，届时只是往序列里插一项，
不改函数签名。源的优先级为：会话 → 分组 → 环境等级隐含默认 → 内置默认。

**逐字段策略（P0 定死，后续期新增字段须在此表落位）：**

| 字段类 | 策略 | 理由 |
|---|---|---|
| 标量（host/port/TERM/超时/编码…） | Override | 语义唯一 |
| `tags` (F63) | **Merge** | 标签本就是多值归属，分组的「生产」应与会话的「web01」共存 |
| 危险命令关键词表 (F65) | **Merge** | 安全类配置只应叠加，不允许会话意外削弱分组的防护 |
| 登录后命令列表 (F41) | **Override** | 拼接会产生「为什么多跑了一条命令」这类极难排查的问题；需要通用命令就在会话里复制一份 |
| 复合对象（`icon`/`color`） | Override，**整体继承或整体覆盖** | 明确不支持字段级部分覆盖（如「只覆盖 hex、沿用分组的作用范围」）。这是硬限制，用一条单测钉死，防止 P2 的 UI 需求把它撑开 |

### 4.2 分组的可继承字段边界

分组持有的默认值集合**只包含**：`appearance`（icon/color）、`safety`（环境等级/危险命令表/只读默认）、
`automation`、`terminal`、`connection` 中的策略类字段（超时/重连/keepalive/代理）。

**明确不可继承**：`host` / `port` / `user` / `auth` / `name` / `id` —— 连接目标与凭据是会话身份本身。
后续各期新增字段一律对照本表落位，不重新讨论。

### 4.3 P0-a：store 地基（纯单测，不碰 GPU / SSH）

- `SessionRecord` 由扁平结构拆成分节嵌套：
  `identity` / `connection` / `auth` / `automation` / `terminal` / `appearance` / `safety`。
- 新增 `GroupRecord`（单层），`SessionRecord` 增 `group_id: Option<GroupId>`。（**F60**）
- 实现 §4.1 的两个 resolve 纯函数。
- `schema_version` + 一次性迁移，迁移前写 `sessions.toml.bak`。
- `secrets.enc` 结构不变（F70 不受影响）。

**两个实现风险（计划阶段必须先验证，不能假定是机械重构）**
1. `AuthKind` 是内部标签枚举（`#[serde(tag = "kind")]`，`model.rs:21`）。
   `toml` crate 对「内部标签枚举嵌套在 table 内」的序列化有已知限制，
   分节重构后可能直接序列化不出来。**先写一个最小 round-trip 验证，再动手重构。**
2. 现结构除 `note` 外均无 `#[serde(default)]`，缺字段即解析失败。
   所以迁移不能靠新结构直接读旧文件——需保留 `SessionRecordV1` 专供读取，再转换。

**验收**
- `resolve_override` / `resolve_merge_list` 各自的三级 fallback 单测。
- 复合对象「不支持字段级部分覆盖」的单测（钉死 §4.1 硬限制）。
- 迁移 round-trip 单测：喂入 v0.1.12 格式的 `sessions.toml`，迁移后逐字段等价，且 `.bak` 存在。
- 删除分组时归属该组的会话 `group_id` 置 `None`（不级联删会话）单测。
- `tests/f70_no_plaintext.rs` 继续绿（迁移不得把口令写进明文文件）。

**架构约束**：resolve 全是纯函数，留在 `mullion-store`（零 UI / 零 async / 仅同步 IO）。

### 4.4 P0-b：代理 + 跳板 + 最小 UI

- `SshConfig` 增 `proxy: Option<ProxyConfig>`（SOCKS5 / HTTP CONNECT，含认证）
  与 `jump: Vec<JumpHost>`。（**F4** / **F5**）
- `establish()` 中把 `TcpStream::connect` 换成可插拔拨号器：直连 / 经代理 / 经跳板。
  跳板机本身可位于代理之后（spec F5 明确要求）。
- 跳板可引用已有会话 id 以复用其凭据 → **必须做环检测**（A 跳 B、B 跳 A）。
- app 侧最小改动：编辑器加「分组」下拉 + 「代理」「跳板」两栏；会话管理器按分组折叠。

**两条同等级的结构性红线**
1. **`open_pty()` 签名不含任何网络参数**——意图写在 `crates/mullion-ssh/src/session.rs:244-246`
   的注释里（adr-009 记录的是一条连接多 channel 的后果与约束，未含此措辞）。
   代理/跳板逻辑只能在 `establish()` 里，绝不能漏进 `open_pty()`。
2. **`mullion_ssh::config::JumpHost` 禁止出现任何 store 类型**（尤其不得有
   `Reference(SessionId)` 变体）。id 解析、凭据取出、环检测全部在 store/app 层完成，
   传入 ssh 的必须是完全物化的 `host/port/auth`。否则 `mullion-ssh` 被迫认识
   `mullion-store`，直接违反单向依赖。**守护方式是 crate 级依赖检查，不能只靠代码审查。**

**验收**
- 拨号器选择的纯函数单测（给定 config → 选出直连/代理/跳板链）。
- 跳板链环检测单测（自引用、二元环、三元环）。
- `mullion-ssh` 的依赖树中不出现 `mullion-store` 的检查。
- 动 SSH 层后重跑 `emulator::tests::pty_write_is_collected`（T1，已升级为 per-pane）。
- **人工验收**（无头环境验不了，属 CLAUDE.md「你无法验证的东西」）：
  Windows 实机经真实 SOCKS5 / HTTP 代理链路连通；`MULLION_LIVE=1` 对内网真机跑 live。

## 5. P1 — 登录后自动化（F40~F44）

- **F40** tmux 自动 attach：`tmux new-session -A -s <name>` 语义（不存在则建），可开关
- **F41** 登录后命令列表（逐行发送，每行可设延时）
- **F42** 初始工作目录
- **F43** 环境变量注入（优先 SSH env 请求，服务端拒绝则回退到 `export` 行）
- **F44** 自动化整体开关（便于临时跳过，排障用）

**三个必须在实现计划阶段定死的问题**
1. **「登录完成」判定**：匹配 shell 提示符不可靠（形态千差万别）。
   采用「首次收到 PTY 输出 + 可配延时」。
2. **分屏语义**：一条连接开 N 个 pane（adr-009），每个 PTY channel 各跑一次自动化。
   tmux 会话名是否附 pane 序号需给出明确规则
   （倾向不附，靠 tmux 自身的多客户端 attach 能力）。
3. **定时写入调度归属哪个 crate**：这是真实 async 行为。
   规定为——**`mullion-ssh` 里一个通用 async 函数，只认 `Vec<(Duration, Vec<u8>)>`，
   不认识 tmux / 自动化语义**；生成时间表的纯函数留在 store。
   绝不能进 `mullion-store`（破坏零 async 红线），也不堆进 app 事件循环（会与 T3/T7 帧率节流打架）。

**一条已知的跨期耦合**：自动化命令的行终止符本属 F25（回车 CR/CRLF，排在 P3-b）管辖，
但 P1 落地时必然要先选一个。**规定：复用当前 `keymap.rs` 里 Enter 键的硬编码约定，
待 F25 落地后两条路径统一改走同一份配置**——不允许出现「人手敲回车」与
「自动化脚本发送」用不同换行约定的情况。

**验收**
- 自动化脚本生成为纯函数：给定 `ResolvedConfig` → 待发送字节序列 + 延时表，单测覆盖。
- tmux 命令拼装的转义单测（会话名含空格 / 引号）。
- 新 pane 建立后仍须发 `window_change`（T4，`app::tests::reflow_emits_resize`）。
- **人工验收**：Windows 实机连上即落在远端 tmux 里的 Claude Code。

## 6. P2 — 组织与防误操作（F61~F69）

P0-a 已备好数据层，本期主体是 egui 侧。**拆两个切片**，因为两半的风险性质完全不同：
P2-a 要引入新的图标资源管线，P2-b 是输入路由逻辑、与 T1/T8 强相关。

### P2-a 组织展示

- **F61** 图标：内置库（发行版 logo 等）+ emoji
- **F62** 语义色板：6~8 个预设（生产/预发/测试/开发/自定义）；允许自由 hex 但默认走色板。
  项目当前只有单一深色主题（`theme.rs` 仅 `MULLION_DARK`，已冻结的视觉基线也是单深色方案），
  故每个语义色只需「常规 / 弱化」两级色阶（分别用于条目底色与边框），

- **F63** 标签 tags（Merge 继承）+ 搜索 + 收藏 + 排序权重
- **F64** 环境等级标记（开发/测试/预发/生产），作为 §4.1 fallback 序列中的一层隐含默认色

色值必须与已冻结的 UI 视觉规格同源，不得另立一套。

**验收**（按子功能拆开，便于逐条回归）
- tags round-trip；收藏与排序权重的持久化。
- `filter(sessions, query, tags, env) -> Vec<SessionId>` 纯函数单测。
- 「常规/弱化」两级色阶取值函数的纯函数单测。
- **人工验收**：内置图标库在 `MULLION_DARK` 下渲染无缺字、清晰可辨；语义色彼此可辨且与前景对比度达标。

### P2-b 防误操作

- **F65** 危险命令二次确认（`rm -rf` / `shutdown` / `reboot` 关键词表，Merge 继承）
- **F66** 只读模式（禁止输入）
- **F67** 是否允许被多会话广播/同步输入包含
- **F68** 剪贴板策略：多行粘贴前确认
- **F69** 连接前确认弹窗

**验收**
- 危险命令匹配纯函数单测（含误报边界：`rm -rf` 出现在字符串字面量里）。
- 只读模式**只拦截键盘/鼠标输入触发的写入，不拦截终端自身产生的应答字节**
  （CPR / DA 等）。若做成「该 pane 的 `PtyWrite` 一律丢弃」就会复现 T1
  ——全屏 TUI 探测收不到应答、永久卡死。只读 pane 下
  `emulator::tests::pty_write_is_collected`（T1）仍须绿。

## 7. P3 — 连接韧性 + 终端/外观可配

四类工作互不依赖，**拆三个切片**：

### P3-a 连接韧性（风险最高，单独走）

**F7** 连接超时、**F8** 自动重连（重试间隔 / 最大次数）、**F9** keepalive + TCP keepalive；
启动时自动连接 / 随工作区恢复。

**为什么排最后**（D4）：引入连接状态机，与「一条连接承载多 pane」耦合最重
——重连后 N 个 channel 如何恢复、迟到的 `PaneOpened` 如何处理，adr-009 已记录这类失效模式。

**验收**
- 重连退避策略纯函数单测（含上限与放弃条件）。
- 回归 adr-009 相关守护测试（`pane_still_wanted` 系列）。
- **人工验收**（CLAUDE.md 明确点名「真实 SSH 链路行为…断线重连」无法自动验证）：
  真实网络抖动 / 代理重启后，N 个 pane 是否全部恢复、P1 自动化是否重新执行、
  tmux 是否原样 attach 回去。

### P3-b 终端行为参数（VT 测试驱动）

**F22** TERM 类型、**F23** 字符编码（UTF-8/GBK/GB18030/Big5…）、
**F24** Backspace/Delete/Home/End 键序列风格 + 功能键映射方案 + Alt as Meta + AltGr 处理、
**F25** 回车 CR/CRLF、**F26** 光标形状与闪烁、**F27** 铃声、
**F28** 鼠标行为（选中即复制/右键）、**F29** 空闲自动断开 + 空闲保活字符。

**验收**
- GBK/Big5 fixture 的 VT 快照测试。
- 键序列风格切换的 `keymap` 单测；**不得破坏 T5/T6**
  （`shift_blocks_mouse_report_so_user_can_copy`、`shift_enter_without_kitty_is_esc_cr`）。

### P3-c 外观覆盖 + 认证增强（纯 UI / 增量）

**F86~F89** 会话级字体、配色、初始尺寸、行高/字间距/连字/粗体处理的覆盖

**认证增强排在此处的理由**：现有三种认证（密码/公钥/agent，F1）已覆盖日常路径，

无前置依赖，可按人力情况前移。

## 8. P4 — 边界外储备区（登记，不实现）

**登记动作在 P0 一并完成**（否则这批条目会在四期期间散落无主）。P4 本身没有代码产出，
它是这张表的持续存在：每期结束时复查一次，看有无条目因边界变化而应上移。

一条勘误：清单 §2 的「禁用 Nagle 算法」**已经实现**——`session.rs` 里
`set_nodelay(true)` 是现有行为，不需要排期。

在 `spec.md` 新增「已登记未排期」表，逐条写*为什么不做* + *重新评估条件*：

- 清单 §1 快捷别名（无命令行快速连接入口，暂无载体）
- 清单 §2 IP 协议族偏好（自动/IPv4/IPv6）——当前走系统默认解析，未遇到问题
- 清单 §2 协议里的「本地 Shell」，以及 Telnet / Rlogin
- 清单 §3 主机密钥策略三态切换（严格/首次接受/忽略）与 `known_hosts` 路径可配
  ——注：`spec.md` 的 `F3-a`（key 未含端口）是既有欠账，与此项相关，仍按 spec 自身排期走
- 清单 §3 的 OTP/TOTP 自动填充、expect/send 登录应答、GSSAPI-Kerberos、PKCS#11 智能卡

## 9. 与架构不变量的关系

- 所有解析、筛选、匹配、拼装逻辑落在 `mullion-store`（纯同步）或纯函数模块，**可无窗口单测**。
- `mullion-ssh` 仍不认识「pane」「会话记录」概念，只接受完全物化的 `SshConfig`
  与 `Vec<(Duration, Vec<u8>)>` 时间表（见 §4.4 红线 2、§5 问题 3）。
- 依赖方向仍为 `app → {core, term, ssh, store}`，本路线图不引入反向依赖。
- 每期新增字段只往 `SessionRecord` 的既有分节里加、按 §4.1 表落继承策略、
  按 §4.2 表判是否可继承，不改顶层形状（D3 的全部价值所在）。
