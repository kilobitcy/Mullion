# 切片 E：布局持久化（F37）设计定案

> 2026-08-13。上游：D 系列（`2026-08-12-sftp-browser-design.md`）已全部完工，
> 标签容器（F36）与分屏树（F30~F35）都已就位，本片只做「把它们记下来、重启摆回去」。

**spec 出处**：F37「布局持久化，重启恢复」，P1，验收「序列化/反序列化 round-trip 单测」。
里程碑 v0.5 的最后两项之一（另一项 F71 主密码不在本片）。

---

## 0. 一句话

关掉窗口时把「开了哪几个标签、每个标签是哪条会话、分屏成什么形状、窗口多大」
记进 `layout.toml`；下次启动把标签栏原样摆回来，**但一条连接都不建**——
每个恢复出来的标签是个占位，用户点「重连」才真的拨号。

---

## 1. 恢复语义：骨架 + 手动重连（**已拍板**）

启动后标签栏里有上次那几个标签，可切换、可关闭、可重排（重排不在本片）。
中央区不是终端，是一句「未连接」+ 上次的分屏形状 + 一个「重连」按钮。
菜单里另给一条「全部重连」。

**否掉「启动即自动重连全部」的三条理由**，都不是洁癖：

1. **启动即执行登录后自动化。** F40~F44 会在连上之后往远端 shell 里发命令
   （`tmux attach`、初始 cd、`export`、用户自配的命令列表）。把它绑在「双击了
   exe」上，等于用户每次开机都对上次开着的 N 台机器各跑一遍脚本——而他这次
   打开 Mullion 可能只是想连第 N+1 台。
2. **高延迟代理链路上 N 条连接互相拖慢。** 本项目的主场景就是高延迟代理链路
   （见 CLAUDE.md 背景）。同时拉 4 条连接 + 4 条跳板链，每条都要完整握手，
   结果是「启动后二十秒里哪个标签都不能用」，比空标签栏更糟。
3. **缺凭据时会连弹 N 个框。** 密码/口令没存在库里的会话，自动重连会在启动
   瞬间叠一摞输入框，而用户还没来得及看清哪个是哪个。

「只自动连上次的活动标签」也否掉了：**「哪个是活动标签」在关窗那一刻往往是
随手切到的**，把它提升成「唯一被自动连的那个」会让恢复结果不可预测。

代价说清楚：用户每次启动要多点一下。这是刻意用一次点击换「启动行为完全可预测」。
将来若确实嫌烦，加的是一个默认关的开关（`自动重连上次的标签`），不是改默认。

## 2. 存哪儿、存什么

### E1 独立文件 `<config_dir>/layout.toml`，不进 `sessions.toml`

`sessions.toml` 是**用户的资产**（会话库、分组、隧道），丢了要重配一遍；
`layout.toml` 是**上次的运行现场**，丢了只是回到空标签栏。两者生命周期和
丢失代价差一个量级，混在一个文件里有两个实打实的坏处：

- 每次切标签/拖分隔条都要重写整个会话库，而 `Vault::save` 是**连加密侧车一起
  写两个文件**——把用户凭据的写入频率从「点保存时」抬到「每帧」。
- 布局解析失败时没法降级：会话库解析失败必须报错，布局解析失败必须静默忽略
  （见 E6）。同一个文件给不出两种失败语义。

`layout.toml` 自带 `schema_version`，与 `sessions.toml` 的版本号**各走各的**——
布局格式的演进节奏跟会话模型无关。

### E2 存的字段

```toml
schema_version = 1
active_tab = 1                      # 下标；越界时夹到 0（见 E6）

[window]
width = 1600.0                      # 逻辑点，inner size
height = 900.0
x = 120                             # 逻辑点，outer position；可缺省
y = 80
maximized = false

[[tab]]
kind = "terminal"                   # "terminal" | "files"
session_id = "7"
title = "prod-web-01"
focus_leaf = 2                      # 前序遍历第几个叶子（0-based）
[tab.tree]                          # 见 E5 的编码
...
```

**不存**（每条都是刻意的）：

| 不存的东西 | 为什么 |
|---|---|
| 终端 scrollback 内容 | 那是远端输出的明文，落盘等于给每台机器的会话内容做了一份无加密副本；F17 从来只承诺内存里的回溯 |
| SFTP 面板的当前目录 | F120 明文写了「**不记忆上次目录**」，默认目录由会话配置决定 |
| 传输队列 / 编辑中的文件 | 传输的对端连接没了，队列项恢复出来是一堆必然失败的条目；编辑中的文件由 D3 的退出确认负责（`edits.blocks_exit()`） |
| pane 的 `PaneId` | 见 E5 |
| 快速连接标签 | 见 E6 |

### E5 树只存**结构**，叶子不存 id

```toml
[tab.tree]
kind = "split"
dir = "horizontal"
ratio = 0.5
[tab.tree.a]
kind = "leaf"
[tab.tree.b]
kind = "leaf"
```

`PaneId` 是进程内计数器（`Workspace::alloc_id`）发的，跨重启没有任何意义：
存了它，恢复时要么跟新发的号撞、要么要维护一张只在恢复那一瞬间有用的映射表。
焦点同理，存的是「前序遍历第几个叶子」——这个序号在同一棵树里跨重启稳定。

### E4 `mullion-store` **不许**认识 `mullion-core`

架构不变量是 `app → {core, term, ssh, store}`，**其余互不依赖**。所以落盘的
树是 store 自己的 `SavedNode`，`mullion_core::layout::Node ↔ SavedNode` 的互转
住在 app 的 `shell/layout_snapshot.rs`。

**这是本片最容易被「图方便」破坏的一条**：往 `mullion-store/Cargo.toml` 里加
一行 `mullion-core.workspace = true`，`SavedNode` 就能直接换成 `Node`，省掉
一整个转换层和它的 round-trip 测试。代价是布局树的两个真源合并——此后
`mullion-core` 每改一次 `Node`（加个 `Tabbed` 变体、把 `ratio` 换成整数千分比）
就同时改了**磁盘格式**，而 core 的作者根本不知道自己在改文件格式。

配守护测试：扫 `mullion-store/Cargo.toml` 的源码，断言里面没有 `mullion-`
开头的依赖。

## 3. 恢复流程

### E9 重连复用 `spawn_connect`，`ConnectOk` 顶掉占位标签

```
用户点占位标签上的「重连」
  → App 记下 pending_restore = { tab_id, tree }
  → 走既有的 spawn_connect（同双击会话，一条路径不分叉）
  → ConnectOk 抵达：
       有 pending_restore 且 tab_id 还在  → 把占位标签**原地换成**真标签
       否则                               → 照旧开新标签
  → 按 tree 调 Workspace::apply_saved_tree，对返回的每个新 PaneId 开 channel
```

「原地换」而不是「关掉占位再开新的」：后者会让标签**跳到最右边**，用户点的
是第 2 个标签，连上之后它跑到了第 5 个位置。

**既有守护测试不许削弱**：`connecting_opens_a_new_tab_instead_of_replacing_the_active_one`
钉的是「在 A 上连 B 不许掐掉 A」。本片给 `ConnectOk` 加的分支必须**只在
`pending_restore` 命中时**才替换，且替换的是 `pending_restore.tab_id` 指名的
那个标签，**不是活动标签**——用户点了「重连」之后完全可能切到别的标签去等。
这两条各配一个测试。

### E10 `Workspace::apply_saved_tree`

与既有 `apply_preset` 同款签名与语义：算出「要开几个新 pane」，把新 id 填进
树，返回需要调用方去开 channel 的那批 id。恢复的是**形状与 ratio**，
pane 里的内容一律是新的。

### E8 窗口几何要夹回可见区域

保存时的显示器可能已经拔掉、改了分辨率、或笔记本从扩展屏回到了单屏。
恢复前拿 `available_monitors` 求各显示器工作区的并集：

- 保存的窗口矩形与任何显示器**都无交集** → **丢弃位置，只用尺寸**，让窗口
  管理器自己摆。不做「夹到最近的边」——夹出来的位置多半压在任务栏下面或
  贴着屏幕边缘，比让 WM 摆更差。
- 有交集 → 原样恢复。哪怕只露出一角也是用户自己拖成那样的。

尺寸另有下界（`MIN_W`/`MIN_H`）：保存到一个 0×0 或 20×10 的尺寸（最小化时
Windows 会送 `Resized(0,0)`，见 `window_state.rs`）恢复出来就是个抓不住的窗口。

纯函数 `clamp_to_monitors(saved, &[MonitorRect]) -> Restored`，可单测。
**winit 的 `MonitorHandle` 不进这个函数**——它构造不出来，进来这个函数就只能靠人眼验。

## 4. 失效模式（E6/E7）

### E6 丢弃规则：布局文件坏了绝不挡住启动

| 情况 | 处置 |
|---|---|
| 文件不存在 / 解析失败 / `schema_version` 不认识 | **当作没有上次布局**，空标签栏启动，日志记一行 |
| 标签的 `session_id` 在会话库里查不到（会话被删了） | 丢弃这个标签，其余照常恢复 |
| 快照时 `session_id == None`（快速连接 F47） | **不入盘**——没有会话记录，重启后无从重建 |
| 树里叶子数为 0 | 丢弃这个标签（树结构损坏） |
| `active_tab` 越界（前面丢了标签） | 夹到 0 |
| 恢复出来一个标签都不剩 | 空标签栏，与「没有上次布局」逐字等价 |

**为布局文件挡住启动是本末倒置**：它不是用户资产，它坏了的正确表现是
「这次没恢复」，不是「打不开客户端」。这条要配一个「喂进去一坨垃圾字节，
断言返回空布局而不是 Err」的测试。

### E7 落盘时机：脏标记 + 节流 + 退出兜底

打脏的动作：开标签、关标签、切标签、分屏、关 pane、拖分隔条、窗口 resize/move。

**不每次立刻写**：拖分隔条是每帧都在变的动作，而 `write_atomic` 是
「写临时文件 + rename」——每帧一次等于每秒往磁盘扔上百个文件。
节流 2 秒，退出路径（`CloseRequested`）无条件兜底写一次。

纯函数 `should_flush(dirty, since_last_ms) -> bool`，可单测。

**已知不覆盖**：进程崩溃 / 被任务管理器杀掉时，最后 2 秒内的布局变化会丢。
这是刻意的取舍——为了这 2 秒把写盘频率抬回每帧不划算，丢的后果也只是
「恢复出来的分屏比例是两秒前的」。

## 5. 这一片能验什么、不能验什么

**能在无头容器里真验**（本片绝大部分）：
- `SavedLayout` 的 TOML round-trip（spec 点名的验收标准）
- `Node ↔ SavedNode` 互转的 round-trip（含嵌套、含 ratio 精度）
- 丢弃规则六条
- `clamp_to_monitors` 的各种显示器拓扑
- `should_flush` 的节流判据
- `apply_saved_tree` 算出的「要开哪几个 pane」

**验不了、要人工确认**：
- 真的关窗再开，标签栏是不是原样（含窗口尺寸/位置/最大化）
- 多显示器：在副屏关窗、拔掉副屏、再开，窗口有没有跑到看不见的地方
- 点「重连」之后分屏形状对不对、每个 pane 是不是都真的连上了
- 「全部重连」在 4 个标签下的表现（会不会把代理链路打爆）
