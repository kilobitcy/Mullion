# 文件面板六项优化（F143~F147）—— 设计

> 2026-08-20 · 基线 v0.1.56
> 触发：实机走查报了六条，其中一条（字形豆腐）是**第三次复发**，要求落盘为机械约束。

---

## 0. 一句话

五项界面缺陷 + 一条全局约束。约束是主菜：`ui/icon.rs` 的模块头**早就记过**这条教训
（走查 P0-5：源码里写的是 `✕`，屏幕上是豆腐块 `□`，所以改自绘），但它只救了那一个按钮，
没变成任何机械检查 —— 于是 `▾`/`▸`/`⟳` 又长了回来。这次补上守护测试。

---

## F143 字形白名单（第 1 项，全局约束）

### 问题

用户报「文件面板/远端/路径/按钮「▾」是方框 □」。

根因与 P0-5 完全一致：`U+25BE ▾` 不在 GB18030 内，微软雅黑没有；egui 内置的
Ubuntu-Light / NotoEmoji / emoji-icon-font 也没有 —— `install_cjk_font` 拼出来的
两级回退链两边都落空，epaint 画出替换字形（豆腐块）。

同类字符在库里还有两处：`transfer_panel.rs:41`（`▾`/`▸` 折叠指示）、
`edit_panel.rs:100`（同上）、`files_panel.rs:520`（`⟳` 刷新，`U+27F3`，同样不在 GB18030）。
用户没报后两处，但它们此刻就是豆腐 —— 只是没人盯着传输面板看。

### 约束（落盘的那条）

> `mullion-app` 的**字符串字面量**里，非 ASCII 字符只允许三类：CJK 汉字、中文标点、
> `ui::glyphs::VERIFIED` 白名单。其余符号一律走 `ui::icon` 自绘。

判据是「该字符在 GB18030 内」—— 那是微软雅黑覆盖面的实用近似，而微软雅黑是
`install_cjk_font` 在 Windows（唯一一等公民）上的第一候选。

### 实现

1. 新建 `crates/mullion-app/src/ui/glyphs.rs`：

   ```rust
   /// 已实机验过的符号白名单。加新的**必须先在 Windows 上看一眼**，
   /// 不许凭「应该有吧」登记 —— 登记这一步就是那道闸门。
   pub const VERIFIED: &[char] = &['★', '☆', '▲', '▼', '→', '…', '·'];
   pub fn is_allowed(c: char) -> bool;   // ASCII / CJK / 中文标点 / VERIFIED
   ```

   白名单初值只是起点，**最终内容由守护测试第一次跑出的实际违规集逐条裁决**：
   在 GB18030 内 → 登记进白名单；不在 → 改自绘。

2. 守护测试 `crates/mullion-app/tests/glyph_whitelist.rs`：

   - 用 `proc-macro2`（dev-dependency，已在依赖树里）把 `src/**/*.rs` 解析成 token 流，
     **只取 `Literal` 中的字符串/字符字面量**。
   - **必须跳过 `#` 之后的 attribute group**。`///` 文档注释在 token 流里表现为
     `#[doc = "..."]`，是货真价实的字符串字面量 —— 不跳过的话 `icon.rs` 模块头里
     那句「源码里写的其实是 `✕`」会让这条测试当场假红。这是本项目记过的
     「源码扫描类守护会假红：注释里举反例」的第三种形态，代价是一整轮排查。
   - 违规报文要给出「文件:行 + 字符 + 所在字面量」，否则一条 `U+XXXX` 谁也定位不了。

3. 现有违规改自绘。`ui/icon.rs` 新增三个 `Glyph`：

   | Glyph | 替代 | 落点 |
   |---|---|---|
   | `Refresh` | `⟳` U+27F3 | `files_panel.rs:520` 刷新按钮 |
   | `TriangleDown` | `▾` U+25BE | 书签下拉 `menu_button`、`transfer_panel`/`edit_panel` 展开态 |
   | `TriangleRight` | `▸` U+25B8 | `transfer_panel`/`edit_panel` 折叠态 |

   `shapes()` 的 `match` 是穷尽的，加变体漏画会编译不过 —— 沿用既有保护。
   新变体照 `every_glyph_stays_inside_its_rect` 的既有断言一起守（该测试遍历
   一个手写数组，**加变体时必须同步那个数组**，否则新图标画出界没人知道）。

   书签那处是 `ui.menu_button("▾", ..)`，换图标需要一个「图标版 menu_button」：
   用 `ui.menu_image_button` 不可行（那要 `ImageSource`），改成
   `egui::menu::menu_custom_button` + 自绘按钮体。

### 不做

- 不改 `install_cjk_font` 去装第二套符号字体。多一份 4MB 字体只为几个三角形，
  而且在没装微软雅黑的机器上照样落空 —— 自绘是唯一不受字体覆盖面影响的做法。
- 不扫 `mullion-core`/`term`/`ssh`/`store`：那几个 crate 零 UI，字符串不进 epaint。

## F144 面板内容不贴裁剪边（第 2 项）

### 问题

用户报三条，同一个根因：

- 「文件面板/本地/路径」上下左右都顶着边；
- 「↑」按钮左侧 1/4 圆弧看不见；
- 路径条右侧控件的顶部线条看不见。

`content()` 把可用区一分为二，每栏拿到的 rect 同时当 `max_rect` 和 `clip_rect`
（`ui.set_clip_rect(left/right)`）。控件从边界那一像素起画，圆角描边的外半像素落在
rect 之外，被 clip 掉 —— 视觉上就是「圆弧缺一角」「顶边少一条线」。

### 修法

`clip_rect` **维持原 rect 不动** —— 那是 B1 定的硬约束（不裁的话本栏的滚动条和超宽
内容会一路画进隔壁栏，`the_two_columns_get_independent_non_overlapping_scroll_areas`
守着）。改的是 `max_rect`：内缩 `SP_XS`（左右）与 `SP_XS`（上），内容因此从裁剪边
往里让出 4pt，描边有地方落。

侧栏（`sidebar()`）走 `allocate_ui` 分两栏，同样处理。

### 守护

判据取**真值**（沿用 F138 那条的做法）：取「↑」按钮的 `Response::rect`，向外扩 1pt
（覆盖描边宽度）后必须完全落在本栏 `clip_rect` 内。不比常量、不比 margin 参数 ——
那是拿常量断言常量。

## F145 书签下拉显示完整路径（第 3 项）

用户点「▾」看到的应当是绝对路径，不是文件夹名。

- 菜单项主文本从 `b.name` 改成 `b.path`。
- `b.name` 非空**且与路径不同**时，hover 显示它（用户自己起的名字不该丢）。
- 原来的「空名回退显示路径」逻辑随之反转：主文本恒是路径，不存在空的情况。
- `bookmark_default_name` 只影响新建收藏时存进 store 的 `name`，**不动** —— 那是
  数据层的默认值，跟这里显示什么无关。

## F146 本地栏不画属主列（第 4 项）

### 判据：按栏静态，不按数据

`files/local.rs:61-62` 构造 `Entry` 时 `uid`/`gid` **恒填 0** —— 本地栏的属主列在数据源
头上就注定是假的（画出来是 `0:0` 或误导性的 `root:root`）。所以 `PanelColumn::Local`
永远不画属主列。

不用「本栏所有条目 uid==0 && gid==0 就隐藏」这种动态判据：远端一个全 root 的目录
（`/etc` 之类很常见）会莫名其妙少一列，切个目录又冒出来，列宽跟着跳。

### 实现

`col_lefts` 加 `PanelColumn` 入参，本地栏返回 4 列。它是**列布局的唯一真值来源**，
`content_w` / `col_w_mut`（列宽拖拽的序号映射）/ `header_at` / `row` 全部跟着改走
同一份 —— 这条「不许在别处再写一遍累加」的既有约束不动。

`ColWidths` 保持 5 个字段、全局一份（远端栏仍要属主列宽），本地栏只是不消费
`owner` 那一个字段。

### 守护

- 本地栏渲染结果里不出现「属主」列头；远端栏出现。
- 本地栏第 4 个拖拽热区（属主列右边界）不存在 —— 否则拖到栏尾会改一个看不见的列宽。

## F147 列尾排序标识 + 逐列可排序（第 5、6 项）

### 第 6 项：标识画在列尾

`header_at` 现在把 `label` 和 `mark` 拼成一个串再 `elide`，标识紧跟标题。改成两次
`painter.text`：

- 标识：`Align2::RIGHT_CENTER` 画在 `rect.right() - SP_XS`；
- 标题：左对齐，可用宽度 = `w - SP_XS*2 - 标识宽 - SP_XS`，再 `elide`。

宽度不够时**标识恒显、标题截断**（已拍板）：标识是「当前按哪列排」的状态指示，
截掉等于状态不可见；标题少两个字仍认得出。

### 第 5 项：大小 / 修改时间可排序

`click_header` 是通用的，`col_lefts` 给五列各配了 `SortKey`，3291 行的既有测试证明
「名称」列点得中。**目前没能重现「大小/修改时间不能排序」**。

处置：先写覆盖 **5 列 × 两栏**的守护测试（首点 → `sort_key` 等于该列；再点 → 方向
翻转）。

- 全绿 → 第 5 项的真实成因是标识被 `elide` 截掉、用户看不出排序生效了，F147 前半
  已经解决，测试留作回归网。
- 某列红 → 就地修命中问题（大概率是 F135 那批列宽拖拽热区吃掉了列头点击 ——
  它们注册在列体之前，边界 ±3pt）。

**结论以实际跑出来的为准，不预先编一个「已修复」。**
