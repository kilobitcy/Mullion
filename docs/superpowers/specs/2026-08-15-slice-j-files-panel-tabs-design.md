# 切片 J —— 文件面板与标签栏打磨（设计）

> 2026-08-15。上游是一次实机走查提出的 6 组问题；本文只覆盖其中 3 组（问题 1 / 2 / 6）。
> 另外 3 组拆去了后续切片，见 §0.2。

## 0. 范围

### 0.1 本切片做什么

一句话：**把文件面板和标签栏上「用起来不对劲」的地方一次修掉**，不动数据模型、不动
架构不变量。全部改动落在 `mullion-app`（少量落 `mullion-ssh` 的错误分类），
`mullion-core` / `mullion-store` 零改动。

十二项，分七组：

| 组 | 内容 | 来源 |
|---|---|---|
| A | 两栏方位调转成「本地在前、远端在后」 | 问题 1-d |
| B | 三个真 bug：滚动条串栏 / 列头排序点不中 / 断联后点目录报错 | 问题 1-c、1-e、1-f、1-g |
| C | 内置编辑器可拖可缩 + 最大化 | 问题 1-h |
| D | 文件类型图标 + 属主列 | 问题 1-a、1-b |
| E | 标签栏：整块可点 / 双击改名 / 右键配色 | 问题 2 |
| F | `modal_open` 改成结构性判据（C 的前置） | 问题 1-h 的真实根因 |
| G | 按 F80~F85 视觉规格审标签栏与两栏，当场修 | 问题 6 |

### 0.2 本切片不做什么

走查里另外三组需求已确认拆走，**本切片一律不碰**：

- **切片 K**：SSH 会话与 SFTP 会话的分组分离（`GroupRecord` 加类型维度，schema v10 + 迁移）
- **切片 L**：SFTP 分屏（问题 3）+ 分屏后变更节点（问题 4）。它需要先决定
  「`FilesTab` 要不要长出 `Workspace`」这个架构级问题，得配 ADR
- 顺序已拍板：**J → K → L**

因此本切片里任何「顺手为将来的分屏铺路」的抽象都是超范围的。`PanelFrame` 仍然是
「一个标签一份两栏状态」，不预先泛化成 N 份。

## 1. A 组：两栏方位

### A1 目标方位

| 宿主 | 现状 | 改成 |
|---|---|---|
| 标签宿主 `content()`（左右并排） | 左远端 / 右本地 | **左本地 / 右远端** |
| 侧栏 `sidebar()`（上下堆叠） | 上远端 / 下本地 | **上本地 / 下远端** |

依据：WinSCP / FileZilla 的既有心智模型是「本地在前、远端在后」，两个宿主用**同一条**
规则而不是两条。

### A2 为什么这是纯粹的调用顺序改动

`show()` 的三个「只对远端栏成立」的参数——`bookmarks`（F120 书签条）、`show_owner`、
`drop_in`（F52 拖入上传）——判据**已经**是 `PanelColumn` 枚举或由调用方按栏别传值，
不是位置也不是 `id` 那个中文字符串。所以本组只调换 `content()` / `sidebar()` 里两次
`show()` 调用的先后，不动任何判据。

**反例（不许这么改）**：拿 `id == "远端"` 之类的字符串当判据。`files_panel.rs:224-227`
已经记过这条陷阱——拿显示用的中文标签当权限开关，改个措辞就会让本地栏长出删除远端
文件的菜单。

### A3 侧栏高度分配

现状是上面那栏（远端）占 `available_height * 0.6`。方位调转后**比例跟着远端走**，
不跟着位置走：**上（本地）0.4 / 下（远端）0.6**。

理由：侧栏的使用场景是「终端为主 + 文件为辅」，辅助视图里远端才是主体，本地栏只是
拖拽的另一端。若比例跟着位置走（上 0.6），等于把更大的面积给了信息量更小的那一栏。

### A4 验收

- 标签宿主：左栏画的是本地目录、右栏画的是远端目录
- 侧栏：上栏本地、下栏远端，且下栏明显更高
- 从资源管理器往窗口里拖文件，落点提示仍然指向**远端**当前目录（F52 规则未变）
- 书签条仍然只在远端栏出现

## 2. B 组：三个真 bug

三个都先走 systematic-debugging 定位根因，**再**动手。本节只定验收判据，不预设修法——
下面「已知嫌疑」仅供起点，若调查结论不同以调查为准。

### B1 滚动条串栏 + 侵入对面栏

**现象**（实机）：远端栏的滚动条画到了本地栏的地盘上；拖左栏的滚动条，滚的是右栏。

**验收判据**：
1. 拖左栏滚动条，只有左栏内容滚动，右栏纹丝不动（反之亦然）
2. 滚动条画在本栏矩形之内，不越过两栏之间那条分隔线

**已知嫌疑**（两条独立，可能同时成立）：
- `files_panel.rs:826-861`：`content()` 自己切 `left`/`right` 两个 `Rect`，再用
  `scope_builder(UiBuilder::new().max_rect(..))` 摆内容。`show()` 里的 `ScrollArea`
  用了 `auto_shrink([false, false])`，需要确认它取的是 `max_rect` 还是父 ui 的
  `available_rect`——若是后者，滚动条会画到 `full` 的右边界上，正好落在对面栏
- `ScrollArea` 的持久化 id 撞车：`scroll_id_salt(id, generation)` 两栏的 `salt` 确实
  不同（`"远端"`/`"本地"`），但最终 id 是 `ui.id.with(salt)`，而两个 `scope_builder`
  子 ui 的 `ui.id` 是否互不相同需要实测确认（`files_panel.rs:204-217` 的文档已经记过
  一次同源问题：跨**标签**的 id 撞车，那次靠掺 `generation` 解决；这次是同一帧内
  跨**栏**）

**测试策略**：这两条都在 egui 内部的几何/id 分配里，纯函数测不到。做法是
在离屏 harness（`ui/annotate.rs` 那套出图设施）里跑一帧，断言两栏的
`ScrollArea` 拿到的 `Id` 不相等、且各自的视口矩形不重叠。若 egui 0.30 不暴露这些，
退而求其次断言 `show()` 内部实际用于分配的矩形宽度不越界，并在 PR 描述里把
「滚动条视觉位置」列进人工验收清单。

### B2 列头点击排序无效

**功能已经存在**：`files_panel.rs:492-527` 的 `header()` 有四个 `allocate_exact_size`
+ `Sense::click()`，点中会调 `state.click_header(k)`，`▲`/`▼` 标记也画了。用户点不出
效果说明**点击没落到列头上**，不是缺功能。

**验收判据**：连点「名称」两次，依次得到 `▲`（升序）与 `▼`（降序），且行序真的变了；
四个列头（加上 D 组新增的「属主」共五个）都能点中。

**已知嫌疑**：`show()` 开头那个覆盖 `ui.max_rect()` 的背景右键菜单 `interact`
（`files_panel.rs:274-278`）。它注册在最前面，按 egui 同层「后注册压在先注册之上」
本应输给列头；但它的 `Sense::click()` 覆盖全栏，需要确认列头是否真的赢得了这次命中
（尤其在 `ui.horizontal` 里 `allocate_exact_size` 拿到的 rect 是否如预期）。

### B3 断联后点目录报错

**现象**：SFTP 节点标签的连接断掉之后，点目录会把底层错误原样糊到面板上，用户没有
任何回到可用状态的入口。

**设计**：

1. `files::Load` 枚举新增 `Disconnected` 变体（现有：`Idle` / `Loading` / `Ready` /
   `Failed(String)`）
2. 新增**纯函数**错误分类器（放 `mullion-app` 的 `files` 模块，不进 `mullion-ssh`——
   「这个错误该让界面怎么反应」是 UI 决策）：

   ```
   enum FailKind { Session, Path }
   fn classify(err: &str) -> FailKind
   ```

   - `Session`：连接/通道级——channel 关闭、EOF、连接被重置、sftp 会话已终止
   - `Path`：路径级——权限不足、不存在、不是目录

   判据落在字符串上是权宜（`mullion-ssh` 目前把 sftp 错误压成了 `String`）。**这一点
   要在实现时复核**：若 `mullion_ssh::sftp` 已经有结构化错误类型，就按类型分类，
   不要拿字符串匹配。字符串匹配是最后手段，且必须配一组覆盖真实错误文案的单测。
3. `Session` → 该栏转 `Load::Disconnected`，画「连接已断开」+ 一个**重连**按钮；
   `Path` → 维持 `Load::Failed`，只是文案换成人话，当前目录不变
4. 重连走已有那条路径：与 F37 占位标签的「重连」按钮同一个 `spawn_connect` 入口，
   不新造一条拨号链路

**验收判据**：
- 断开连接后点目录 → 面板显示「连接已断开」+ 重连按钮，**不显示底层错误串**
- 点一个没权限的目录 → 仍停在当前目录，提示「权限不足」，**不**转断开态
- `classify` 单测覆盖两类各至少三条真实错误文案

**非目标**：自动重连。理由：可能要重新输密码/口令（主密码锁着就卡死），且高延迟
链路下会反复拨号，要配退避策略——那是独立的一笔。

## 3. C 组：内置编辑器

**现状**（`ui/editor_window.rs:126-162`）：`egui::Window` 带
`.anchor(Align2::CENTER_CENTER, ..)`（锁死位置，拖不动）+ `default_size(720, 480)` +
编辑区 `ScrollArea::max_height(360.0)`（写死）。

**改成**：
1. 去掉 `.anchor(..)` —— 窗口可拖动
2. 去掉 `max_height(360.0)` —— 编辑区高度由「窗口当前可用高度减去头部与底部按钮行」
   算出来
3. 标题行加一个「最大化 / 还原」切换：最大化时窗口铺满主窗口客户区，再按一次回到
   上一次的大小与位置

**不做**：独立操作系统窗口。本项目是手接的 winit + wgpu + egui（非 egui 框架托管），
多视口要自建第二个 window + surface + 帧循环分支，风险和工作量都远超收益。

**能打字**这件事不在本组——根因是 F 组，见下。

**验收判据**：窗口能拖、能缩、能最大化；最大化后编辑区随之变高（不再停在 360）；
**能打字**（人工验收，见 §7）。

## 4. D 组：图标与属主列

### D1 文件类型图标

新模块 `crates/mullion-app/src/ui/file_icon.rs`，用 painter 自绘三种形状：

| `EntryKind` | 形状 |
|---|---|
| `Dir` | 文件夹（带页签的梯形/矩形） |
| `File` | 页（右上角折角） |
| `Symlink` | 页 + 一个箭头角标 |

**不用 emoji / 字符**：字形是否存在取决于字体，Windows 上会变豆腐块，且字形宽度不可控
会让整列对齐飘掉。自绘不依赖字体。

**颜色**沿用现有语义色，不新造色值（F80 色板已冻结）：目录 `fg_strong`、文件 `fg`、
名称不可操作（非 UTF-8）`fg_dimmer`——与 `row()` 现有的文字取色规则**同源**，
不允许图标和文字用两套判据。

**可测部分**：形状顶点计算抽成纯函数（输入 `rect` + `kind`，输出顶点/线段列表），
单测断言顶点全部落在 `rect` 内、且三种 kind 的输出互不相同。像素长什么样仍是人工验收。

### D2 属主列

列结构从 `名称 | 大小 | 修改时间 | 权限` 变成：

```
[图标] 名称 | 大小 | 修改时间 | 权限 | 属主
```

- 属主固定宽度常量（与 `W_SIZE`/`W_MTIME`/`W_PERM` 同级），**默认显示**
- 内容是 `uid:gid` **数字**。SFTP v3 的 attrs 里 uid/gid 就是数字，而
  `russh-sftp 2.4.0` 的客户端 `DirEntry` 只暴露 `parent`/`file`/`metadata`，
  **不暴露 `longname`** —— 协议层拿不到名字。这与 `mullion-ssh/src/sftp.rs:135-137`
  和设计 D21 记的是同一条事实，本切片不推翻它（不去 exec `id`、不去读 `/etc/passwd`）
- 新增 `SortKey::Owner`，属主列可点排序（同其余四列）
- **原有的 `show_owner` 开关整个下线**：它现在的行为是「默认隐藏 + 列头右键切开 +
  把 `uid:gid` 拼在权限列后面」。属主成为默认可见的独立列之后，这个开关没有意义。
  `PanelFrame::show_owner` 字段、`show()` 的 `show_owner` 参数、列头右键那个菜单项
  一并删除

**注意**：属主列只在远端栏有意义吗？——不。本地栏（Windows）也有属主概念，但
`files::local` 目前给不出 uid/gid，构造 `Entry` 时 uid/gid 恒为 `0`。**本地栏属主列
显示 `—`**，不隐藏该列——两栏列结构一致才能左右对照着看，这正是双栏文件管理器的用途。

判据用 `PanelColumn::Local`，**不是** `uid == 0`：远端真的有 root 拥有的文件，拿 `0`
当「没有属主信息」的哨兵会让远端 root 文件的属主列也变成 `—`。这与 A2 那条「判据用
枚举不用字符串/魔数」是同一条纪律。

### D3 名称列宽度

名称列是自适应列（`可用宽 - 其余列固定宽`）。加了图标与属主列之后，两处计算
（`header()` 与 `row()`）必须**同源** —— 现在它们各写了一遍
`(w - W_SIZE - W_MTIME - W_PERM).max(80.0)`。本组把它抽成一个纯函数，两处都调它，
否则列头与行会错位。这是 G 组走查会命中的问题，提前在这里解决。

## 5. E 组：标签栏

### E1 整块可点

**验收判据**：标签矩形内**任何**不在 `×` 上的点，点下去都能切到该标签。

**已知嫌疑**：`chrome.rs:221-290` 的 `one_tab` 先 `allocate_exact_size` 拿到 `resp`，
之后在 `new_child` 里画图标与标题。需要确认子 ui 里的部件是否吃掉了落在标题区的点击。
（同源问题记忆里有过一次：D4a 修过「标签宿主一行都点不中」。）

### E2 / E3 改名与配色

- **双击**标签 → 打开「标签属性」弹窗
- **右键**标签 → 菜单：`重命名…` / `设置颜色…` / `关闭`。前两项打开同一个弹窗
  （分别把焦点落在名称框 / 调色盘上）
- 弹窗内容：名称输入框 + 颜色选择（egui 调色盘）+ 「应用到哪里」（复用 F62 现有的
  `ColorTarget` 勾选，不新造一套）
- **写回的是会话记录**：`identity.name` 与 `appearance.color`（`ColorSpec { hex,
  apply_to }`）。即「在标签上改名/改色」等价于「在会话管理器里改那条会话」，
  下次连同一条会话仍然生效。零 schema 改动

**没有对应会话记录时**（快速连接、`RestoredTab` 占位标签）：右键菜单里这两项**禁用**，
tooltip 写明原因（「这个标签没有对应的会话记录」）。

**不做**「只对本标签生效的运行期覆盖」：那要新增一份不持久化的标题/颜色状态，与 F37
的布局持久化语义打架（关窗口存的是会话 id，不是标题）。

**不做行内编辑**：标签只有 `TAB_W` 宽，塞不下输入框。

**弹窗必须登记进 F 组的模态表**，否则里面敲的字会漏给远端 shell。

## 6. F 组：`modal_open` 结构性化

### 问题

`app.rs:1853` 的 `modal_open()` 是一串 `||` 列举，当前列了 7 项，**漏了三个**：
内置编辑器（`ui/editor_window.rs`）、文件对话框（`ui/files_dialog.rs`，新建文件夹/
重命名）、分组管理器（`ui/group_manager.rs`——`app.rs:1850-1852` 的注释已经承认了这是
既有缺口）。

后果：这三个弹窗开着时，键盘按 T8 的规则仍被判给终端，用户敲进输入框的字**同时被原样
发给远端 shell**；编辑器里则是压根打不出字。

这是「列举式门控在加档时必然漏」第 4 次踩中（前三次记录在切片 H 等的复盘里）。

### 设计

不再靠人记得加一行 `||`。改成让**编译器**当守护：

```rust
enum Modal {
    SessionManager, About, Settings, Unlock, HostKey, Paste, Import,
    Editor, FilesDialog, GroupManager,
}

impl Modal {
    const ALL: &[Modal] = &[/* 全部变体 */];
}

fn modal_open(&self) -> bool {
    Modal::ALL.iter().any(|m| match m {
        Modal::SessionManager => self.ui.session_manager_open,
        // …每个变体一条臂
    })
}
```

加一种新弹窗时：加变体 → `match` 不再穷尽 → **编译不过**。这比再写一个测试可靠——
测试只能断言「现有这几种登记了」，它对「将来新增的那种」天然恒绿，正是前三次翻车的
形态。

**`ALL` 也要防漏**：`ALL` 少写一个变体编译器不管。配一条测试断言
`Modal::ALL.len()` 等于变体总数（用 `strum` 之类会引新依赖，本项目更适合手写一条
断言 + 在 `ALL` 定义处写明「加变体要同步这里」）。**实现时若发现更好的机械守护
（例如让 `ALL` 由 `match` 推导），优先用那个。**

### 验收判据

- 编辑器 / 新建文件夹 / 分组管理器三个弹窗开着时，敲键盘：字只进输入框，**不**出现在
  远端终端里（人工验收，见 §7）
- 三个弹窗开着时按 `Ctrl+W` 不会关掉背后的标签（`shell::tabs::hotkey` 让位，
  可自动测）
- 删掉 `Modal` 的任一 `match` 臂 → 编译失败（变异验收，实现时手动做一次）

## 7. G 组：视觉规格走查

**判据**：`spec.md` §4.6（F80~F85，已冻结的色板与尺寸）+ `docs/ui-form-guidelines.md`
里那两条与表单无关也成立的纪律：

- 间距只用 `SP_XS/S/M/L/XL` 五档，禁止裸数字
- 颜色只用 theme token，不写字面色值

**审查对象**：标签栏（`chrome.rs`）、远端栏与本地栏（`files_panel.rs`）。

**已经能预见会命中的**：`files_panel.rs` 里 `ROW_H = 22.0`、行内偏移 `4.0` / `8.0`、
圆角 `2.0` / `4.0`、两栏间距 `gap = 8.0`；`chrome.rs` 的 `TAB_*` 系列。

**产出**：清单（哪一处、违反哪条、严重程度）+ **当场收敛到档位**。收敛时不许为了
凑档位改变实际观感超过一档——`22.0` 若收敛到 `24.0` 会让行变高、可见行数变少，
这种要单独标注并在人工验收清单里点名。

**不做**：新写一份「非表单界面规范」文档 + 机械守护测试。那是独立的一笔。
