# SFTP 文件浏览器 + 标签页（F36 / F50 / F52~F59 / F120）

> 2026-08-12。切片 F118/F119（v0.1.31）之后的下一片，代号 **D 系列**。
> 相关：F118（SFTP 节点档，本切片解除它留下的闸门）、adr-009（一条连接多 channel）、
> adr-010（隧道独占连接）、F119（表单布局规范）、F100（标注登记）。
> **F51 在本切片被移出范围**，理由见 D14。

## 背景

F118 把 SFTP 节点做成了会话管理器的第三档，但连接入口是置灰的——`session_map.rs`
遇到 `Protocol::Sftp` 直接返回 `SftpNotSupported`，`editor.rs` 用 `SFTP_NOT_YET`
把「连接」按钮按死。库里现在能存 SFTP 节点，却连不上去。

本切片补齐 spec §4.4 的传输本体，并顺带吃下 F36 标签页——不是顺手，是被逼的：
SFTP 节点连上之后需要一块地方安放，而 `App` 至今只有一个 `ws: Option<Workspace>`
（`app.rs:127`），要么替换掉正在跑的终端，要么就得有标签。

范围比 spec 原先设想的大：双栏（不是单栏侧栏）、拖出到资源管理器（spec 没提）、
内置编辑器（F53 原文只有外部编辑器）。这些是 2026-08-12 grilling 里逐条确认的
需求扩张，各自有新编号（F58/F59/F120），不是自作主张。

---

## 决策

### D1 一套面板，两个宿主

`FilePanel` 是一个与终端无关的组件。两种宿主：

- **侧栏模式**：SSH 会话的右侧栏，`Ctrl+Shift+F` 开关，宽度可拖、按会话记住。
- **标签模式**：SFTP 节点连上后独占一个标签页的内容区。

两者共用同一份列表、拖拽、右键菜单、传输入口代码，差别只有容器方向（D4）与
连接来源（D5）。

否掉的备选：

- **只做侧栏**（spec F50 字面）：F118 造出来的 SFTP 节点点「连接」时无处可去，
  语义悬空。
- **只做独立视图**：SSH 会话里就没有文件浏览了，而「边看 tmux 边翻文件」恰恰是
  最高频的用法。

### D2 面板**不进布局树**

`mullion-core` 零改动。面板是 egui 的 `SidePanel` / 标签内容区，布局树完全不知道
它存在；开关侧栏 → 终端可用区变窄 → 走既有 reflow 发一次 `window_change`。

守护：T4 的 `app::tests::reflow_emits_resize` 覆盖这条路径，开关侧栏后必须复跑。

否掉的备选：**给 `PaneState` 加 kind（Term / Files）让面板成为一种 pane**。分屏、
焦点、preset 能免费复用，但 `pump` / `reflow` / `render` / `input_route` /
`window_change` 处处假设 pane 里有 `Emulator`，八处要加分支；更糟的是把 glyphon
自绘终端和 egui 控件混进同一棵树的渲染路径。收益（面板能和终端拖拽分屏）在本项目
的核心场景里几乎用不上。

### D3 F36 标签页最小版，且**单独成片、零 SFTP 代码**

`App.ws: Option<Workspace>` → `Vec<Tab>` + 活动下标。标签类型两种：终端工作区 /
SFTP 文件视图。快捷键 `Ctrl+Tab` 切换、`Ctrl+W` 关闭、`Ctrl+1..9` 直达。标题 =
会话名，带节点色（F62）与图标（F61）。

**不做**：拖拽重排、标签内嵌标签、重启恢复（那是 F37，独立）、分离窗口。

这一步扫过 `app.rs`（3451 行）的事件循环，而 T3（帧率闸）/ T7（`WaitUntil` 复位）
两条红线就住在那里。所以它是独立切片 D0，掺任何 SFTP 逻辑进来都会让 bug 定位失效。

验收补充（写进 spec F36）：**切标签不断连接**——切换前后底层 SSH 连接数不变。

### D4 双栏；侧栏上下堆叠，标签左右并排

远端栏 + 本地栏，两栏之间互拖即传输。

- **侧栏模式**：上下堆叠（上远端 60% / 下本地 40%，分隔条可拖并记住）。
- **标签模式**：左右并排。

侧栏典型宽 320~450px，左右并排后每栏只剩 160~220px，四列排不下；而把侧栏加宽到
560px 会压扁终端列数，让远端 TUI 重排得很难看。上下堆叠保住了「双栏 + 互拖」的
统一心智，又不动终端宽度。

### D5 本地栏只做导航与传输端点

本地栏能进目录、显示、作为拖放源/目标、「在资源管理器中打开当前目录」。
**不提供本地删除 / 重命名 / 新建**。

理由是风险不对称：Windows 上删除应进回收站（要 `IFileOperation`，不是
`fs::remove_file`），在我们这儿是一行代码，在用户那儿是丢数据；而本地文件管理，
用户已经有一个比我们能写的更好的工具。

### D6 连接：侧栏蹭会话连接，节点独占连接

- **侧栏模式**：复用当前会话的 `Arc<SshConnection>`，`channel_open_session` +
  `request_subsystem("sftp")`。不重握手、不重认证——高延迟代理链路上这是几秒的差别。
  会话断则侧栏灰掉，符合 adr-009。
- **标签模式**：`establish` 一条独占连接，自己的状态机与退避重连，符合 adr-010。

`channel_open_session` 只要 `&self`，会话那条 `Arc<SshConnection>` 给得出来——
隧道 `-R` 撞上的 `&mut self` 限制在这里不存在（已核实 russh 0.54.5）。

### D7 SFTP **不参与隧道**

SFTP 连接不请求 `tcpip_forward`，不能被隧道选作「经由」（F118 已把经由列表限定为
SSH，本切片不放开）。隧道能力只挂在 SSH 会话上。

### D8 协议层用 `russh-sftp 2.4.0`，接受其串行吞吐

已核实：`russh-sftp` **不依赖 russh 本身**（依赖只有 bytes/chrono/dashmap/serde/
log/tokio），吃任意 `AsyncRead + AsyncWrite`，与我们锁定的 russh 0.54 不会打架。

它的读写是请求-应答**串行**的（社区存在 `bssh-russh-sftp` fork 专门加 pipelined
I/O，即为佐证）。RTT 200ms 时单流吞吐约 32KB/RTT ≈ 160KB/s。

**明确接受**，不改协议层、不 fork。缓解手段是 F56：**同一条 SSH 连接上开多条
sftp channel**，默认 4 并发、可配 1~8，让队列里不同文件并行跑。单文件分块并发
（自己切块 + 多 handle）留作将来，不在本切片。

### D9 拖拽三类，各有各的技术路线

| 类型 | 路线 |
|---|---|
| 栏间拖 | egui 0.30 的 drag payload，纯内部，无平台代码 |
| 拖入（F52） | winit `DroppedFile`；**忽略落点**（见下） |
| 拖出（F59） | 专用 STA 线程 `DoDragDrop` + 虚拟文件（见 D10/D11） |

**拖入忽略落点**是被迫的：winit 0.30 的 `DroppedFile` 不带坐标，
`egui::DroppedFile`（`egui-0.30/src/data/input.rs:358`）只有 `path` 字段，而
Windows 在 OLE 拖放期间不发 `CursorMoved`，最后已知指针位置也不可靠。所以规则是
**不管扔在窗口哪儿，一律上传到远端栏当前目录**；拖入时整个远端栏描边 + 顶部提示
「松开上传到 /path/to/cwd」，让规则先于动作可见。

### D10 拖出**绝不能在 winit 回调栈内启动**

`winit-0.30.13/src/platform_impl/windows/event_loop/runner.rs:208`：`send_event`
对 `RedrawRequested` **绕过事件缓冲直接调用 handler**，而 `call_event_handler` 里
`event_handler.take().expect("either event handler is re-entrant (likely)...")`。

结论：在 winit 回调里启动任何嵌套模态消息循环（`DoDragDrop` 正是如此），期间任何
一次 WM_PAINT 都会让进程 panic。拖动时窗口必然重绘，这不是概率问题。

所以拖出走**专用 STA 线程**：单开线程 → `OleInitialize` → `DoDragDrop`。UI 线程
全程不进嵌套循环。风险（明确记录）：拖拽线程与 UI 线程输入队列分离，鼠标跟踪可能
需要 `AttachThreadInput`；**这套东西无头环境一行都验不了**。

否掉的备选：**把事件循环重构成 `pump_events` 模式**以便在回调外调用。彻底但要重写
`app.rs` 事件循环——T3/T7 两条红线所在。为一个手势重写项目最脆弱的部分不划算。

这条要补进 `docs/gui-render-gotchas.md`。

### D11 拖出用虚拟文件（延迟渲染），不预先落盘

`IDataObject` 提供 `CFSTR_FILEDESCRIPTOR` + `CFSTR_FILECONTENTS`，资源管理器落下时
才向我们要 `IStream`，边下边喂。手感是拖出瞬时开始，不需要「先等下载完再能拖」。

`IDataObject` / `IStream` 用 `CoCreateFreeThreadedMarshaler` 做成 free-threaded，
让目标进程在**它自己的线程**直接调 `IStream::Read`——既不经我们的 UI 线程，也不经
拖拽线程的消息泵，UI 全程不冻。

明确接受的代价：部分目标程序只认 `CF_HDROP`，拖过去可能失败或落 0 字节文件，而
失败发生在别人的进程里。补偿手段是 **D12 的日志**。

COM 绑定用依赖树里已有的 `windows` 0.59 + `windows-implement`（wgpu/winit 的传递
依赖，已在 `x86_64-pc-windows-gnu` 下编译通过），不引第三个版本。

### D12 拖出全流程打点日志

接 adr-008 的 `log` facade，target `mullion::sftp::drag_out`，级别走 `MULLION_LOG`：

- 手势判定（起点坐标、拖动阈值、选中项数与总字节）
- 拖拽线程启动 / `OleInitialize` 结果
- `IDataObject::GetData` 每次被问的格式（记录目标程序要的是哪种）
- `IStream::Read` 每次的 offset / 请求字节 / 实际返回 / 耗时（debug 级）
- SFTP 侧读错误、对端取消（`DRAGDROP_S_CANCEL`）
- `DoDragDrop` 返回码与总耗时

这是唯一能诊断「拖到某个程序里没反应」的手段，不是可选项。

### D13 编辑：右键双入口，双击 = 外部编辑

右键菜单两项**外部编辑** / **内置编辑**，不靠双击猜意图。双击文件 = 外部编辑
（`ShellExecute`，与资源管理器一致，对 .png 也说得通）；双击目录 = 进入。

**回传语义（F53 修订）**：自动回传 + 冲突检测。回传前 `stat` 远端，若 mtime/size
与下载时记录的不一致，**不覆盖**，弹冲突提示（保留远端 / 覆盖远端 / 另存副本）。

- 监视生命周期：进入「编辑中」列表后持续监视 mtime，直到用户显式「结束编辑」。
  **不靠猜编辑器进程退没退**——VS Code 一个进程开一堆窗口，进程信号毫无意义。
- 退出清理：程序退出删临时目录；仍有「已修改未回传」时退出前拦一次确认。
- 临时文件：`%LOCALAPPDATA%\Mullion\edit\<会话名>\<远端路径 hash>\<原文件名>`。
  保留原文件名，编辑器的语法高亮才认得出类型。

### D14 F51（跟随 cwd）移出范围

砍掉，理由三条，缺一不可：

1. `vte 0.15` 的 `osc_dispatch` 只认 OSC 0/2、4、8、10~19、52、104，**没有 OSC 7**，
   我们要自己截一层。
2. Ubuntu 的 bash 默认 `PROMPT_COMMAND` 根本不发 OSC 7（那是 `vte.sh` 干的事）。
3. 就算发了，tmux 会自己吃掉它去更新 `pane_current_path`，**默认不向外层透传**。

本项目主场景恰恰是「远端 tmux 里的 Claude Code」，三条叠加等于恒失效。

替代：**书签 + 可配置默认目录**（D15）。**不记忆上次目录**（明确要求）。

取消条件（写进 spec 储备区）：将来若做 tmux 深度集成（能直接问
`#{pane_current_path}`），可以重提。

### D15 书签与默认目录挂在 `SessionRecord`，schema v7 → v8

新增字段：默认远端目录、默认本地目录、远端书签列表（名称 + 路径）。缺省为空。

- 留空时远端默认 `.`（登录后的 home），本地默认 `%USERPROFILE%`。
- 编辑页新开「SFTP」分节，按 F119 表单规范（分节 + 88px 标签列 + `field_w` 三档
  宽度 + `SP_*` 五档间距）。
- 迁移 v7 → v8：新字段缺省，其余逐字节等价。

否掉的备选：**全局书签表**。`/data/Mullion` 这种路径换台机器没有意义；点全局书签
还要先问「在哪台机器上打开」，多一步。

### D16 远端路径的真源是 `Vec<u8>`

SFTP v3 的文件名就是字节串，没有编码约定；Linux 上文件名可以是任意非 UTF-8 字节。

**纪律**：所有 SFTP 请求（打开、删除、重命名、下载源、列举）一律用**原始字节**；
UI 显示串是 `from_utf8_lossy` 的**投影**，只用于渲染。一旦某处拿显示串反推路径，
非 ASCII 文件名就会静默失败——在中文目录下必然发生。

守护测试：假服务端里放一个非 UTF-8 文件名，断言「显示是 lossy 的」且「删除请求
发出的字节 == 原始字节」。

下载到 Windows 时若目标名非法（含 `\ / : * ? " < > |`、以空格或点结尾、`CON`/
`PRN`/`AUX`/`NUL`/`COM1`~`LPT9` 保留名），**打断并给建议名**让用户确认，
**不静默改写**——静默改写会让 F53 的回传对不上原文件，这是最阴的一类 bug。

### D17 删除：链接不跟随；递归先 exec 后回退

- **删除符号链接绝不跟随**：删的是链接本身。列举用 `readdir`（不解引用），显示
  目标靠 `readlink`。**守护测试**——搞错了就是把远端整个目标目录删了。
- **递归删除（F57）**：先试 `exec rm -rf`，被拒或失败则回退 SFTP 逐文件递归。
  sftp-only 账号（`ForceCommand internal-sftp` + `ChrootDirectory`）会拒绝 exec，
  一律走 exec 的方案在那种账号上功能残缺；一律逐文件则删 `node_modules` 要等到
  天荒地老（每文件一个 RTT）。
  路径转义：单引号包裹 + 内部单引号转义（`'\''`），**有守护测试**覆盖含空格、
  引号、换行、`$`、反引号的文件名。
- **无回收站**：远端删除不可逆，确认弹窗里明说，不假装有后悔药。确认文案按 F119
  危险措辞规范：列出「将删除 N 个文件 / M 个目录」+ 完整远端路径，按钮写「删除」
  不写「确定」。
- 递归删除**不进传输队列**（它不是传输），走带取消的模态进度。

### D18 传输队列全局、跨标签存活

底部可折叠面板（状态栏之上），折叠态一行摘要（`↑2 ↓1 · 3.2MB/s · 剩余 00:41`）。
队列项：方向、文件名、源/目标会话、进度、速度、取消 / 重试。

- **跨标签**：切标签、关标签都不影响队列；关标签时若该会话还有传输在跑，拦一次确认。
- 单文件失败不掐整个队列，标红留在列表里可重试；断线整批置「已中断」，重连后可
  一键重试。
- 同名冲突默认弹一次询问（覆盖 / 跳过 / 重命名 / 全部应用），**不静默覆盖**。
- **不做断点续传**（默认关）：续传要保证「本地已下载前缀」与远端当前内容一致，而
  我们没有廉价校验手段（远端不一定有 `sha256sum`，SFTP 也没有部分校验请求）。为省
  几十秒去赌一个静默损坏的文件不划算。将来可做成「大文件（>50MB）断点续传」的知情
  开关，默认关。

### D19 半成品文件：`.mullion-part` 临时名，覆盖时退化为直接写

- 新建目标：传输写到 `名字.mullion-part`，**完成后才 rename** 成目标名；取消/断线
  删掉 `.part`。目录里永远看不到半截文件。
- **覆盖已存在文件时改为直接写**（不走 `.part` + rename）：rename 会换掉 inode，
  丢失原文件的属主 / 权限 / ACL / 硬链接——对 `/etc/nginx/nginx.conf` 这类文件是
  实打实的破坏。与 D20 内置编辑器的写回策略一致。
- 取消时的清理动作写进日志，便于事后对账。

### D20 内置编辑器的五条边界

| 边界 | 取值 | 理由 |
|---|---|---|
| 大小上限 | >1MB 拒绝，提示用外部编辑 | egui `TextEdit` 全量重排，几 MB 每帧卡死，撞 T3 |
| 二进制 | 读到 NUL 即判二进制，右键项置灰 + 说明 | 不给「编辑完把 .png 毁了」的机会 |
| 编码 | 只支持 UTF-8（带/不带 BOM）；非 UTF-8 **只读打开并标注** | 猜错编码保存回去 = 静默毁文件，比不给编辑严重得多 |
| 换行符 | 读到什么保持什么，混合则保持原样只改编辑的行 | 绝不静默转换 |
| 写回 | **直接覆盖**（`OPEN` with `TRUNC`），不做临时文件 + rename | 同 D19：保 inode / 属主 / 权限 |

写前在同目录留 `.mullion.bak`，写成功后删（可关）——兜住「写到一半断线留截断文件」。

### D21 列表显示与操作

- **列**：名称 / 大小 / 修改时间 / 权限 + **属主:组**（默认隐藏，列头右键打开）。
  SFTP 的 attrs 里 uid/gid 是**数字**，协议拿不到 `/etc/passwd` 映射，界面就老实
  显示 `1000:1000`，不为此去 exec 一次 `id`。
- **排序**：默认「目录在前 + 名称升序」，点列头切换；**本地排序**，不请求远端。
- **隐藏文件**：默认隐藏 `.` 开头，`Ctrl+H` 切换，按会话记住。
- **符号链接**：显示 `name → target`；双击指向目录的链接**跟随进入**；删除不跟随（D17）。
- **大目录**：`ScrollArea::show_rows` 虚拟滚动；一次 `readdir` 全量取回（分页拉完），
  过程中显示「已加载 N 项…」；>20000 项提示可能较慢，**不截断**。
- **权限修改**：右键「属性」可改权限（八进制 + 九宫格），走 `setstat`。
  **不做递归 chmod**（那是 exec 的活，风险高、进度不可见）。

### D22 断线重连

- 侧栏模式：跟随会话，无额外语义。
- 标签模式：**自动退避重连**，复用隧道切片的 `schedule.rs`（已跑绿）；重连成功后
  自动回到断线前目录并刷新；期间面板置灰 + 顶部显示「连接断开，12 秒后重试（第 3 次）」。

### D23 入口、位置与快捷键

- **侧栏位置**：右侧（终端内容左对齐，右侧遮挡代价最小），宽度可拖、按会话记住。
- **开关**：菜单项 + 工具栏按钮 + `Ctrl+Shift+F`。选 `Ctrl+Shift+*` 系是因为它在
  终端里不产生控制字符，不和远端 tmux / Claude Code 抢键（T5/T6 类冲突）。
- **终端 ↔ 面板焦点**：`F6`（`Ctrl+Tab` 留给标签页）。
- **面板内**（仅面板有焦点时生效）：`Enter` 进目录 / 外部编辑、`Backspace` 上级、
  `Delete` 删除（带确认）、`F2` 重命名、`F5` 刷新、`Ctrl+H` 隐藏文件、`Tab` 换栏。
- **键盘路由按 T8 纪律**：判给面板的键**绝不先喂 `egui_state.on_window_event`**，
  否则 egui 焦点系统会吞 Tab，终端永久收不到键。
- **F100 登记**：两栏、列头、传输面板、右键菜单项、书签栏全部登记进标注模式，
  否则截图标编号时它们「不存在」。

### D24 解除 F118 留下的闸门

要改（**不是删**，是改成新语义）的三处及其守护测试：

- `session_map.rs` 的 `MapError::SftpNotSupported` —— SFTP 记录改为映射成合法的
  连接参数 + 「连上后开 sftp subsystem」的标记。
- `editor.rs` 的 `Disabled::Sftp` / `SFTP_NOT_YET` 置灰理由。
- 连接意图的兜底闸门。

对应测试从「断言被拒」改为「断言拨号参数正确且不含 PTY 请求」。改动要能自证变红。

## 不做什么

- **不做本地文件管理**（删除 / 重命名 / 新建）——D5。
- **不做 F51 cwd 跟随**——D14。
- **不做断点续传**（默认）——D18。
- **不做递归 chmod / chown**——D21。
- **不做回收站**——D17。
- **不做 F37 布局持久化**：标签不随重启恢复，独立编号独立切片。
- **不做标签拖拽重排 / 分离窗口**——D3。
- **不做单文件分块并发**：并发粒度是「不同文件」，不是「同一文件的不同块」——D8。
- **不做 ZMODEM / 传输模式（ASCII/二进制）**：spec §10 已否，SFTP 覆盖即可。

## 人工验收清单（无头环境验不了，写进各片 Release notes）

- **拖入**：从资源管理器拖文件/文件夹进窗口，是否上传到远端当前目录；提示是否先于动作可见。
- **拖出**：拖到资源管理器 / 桌面 / Office / 聊天软件，是否落地完整文件；拖动期间
  终端是否仍在刷新（UI 不冻是 D10/D11 的核心指标）；失败时日志是否够定位。
- **外部编辑**：双击是否用系统默认程序打开；改完保存后是否自动回传；远端同时被改时
  是否弹冲突。
- **真实链路**：高延迟下的实际吞吐；并发通道 1 → 4 → 8 的差别是否可感。
- **真 OpenSSH 差异**：`internal-sftp` + `ChrootDirectory` 账号下能否浏览；exec 被拒
  时递归删除是否正确回退；`statvfs@openssh.com` 等扩展缺失时是否优雅降级。
- **视觉**：面板与终端的配色/字体是否同源（F80 三处同源纪律）；CJK 文件名对齐。
