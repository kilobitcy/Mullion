# SSH 隧道：端口转发作为一等对象（F110~F117）

> 2026-08-11。新增 `crates/mullion-ssh/src/tunnel.rs`、`socks5_server.rs`；
> `mullion-store` schema v6 → **v7**（新增 `[[tunnel]]`）；
> `mullion-app` 会话管理器新增「隧道」模式、状态栏新增指示器。
> 依赖方向不变（`app → {core, term, ssh, store}`）。

## 背景

spec §4.11 把「隧道转发（-L / -R / -D）与 X11 转发」登记为**不做**，理由是
「与『操作远端 TUI』主线无关；隧道有 `ssh -L` 顶着」，重评条件写的是
「出现高频、需图形化管理的隧道需求」。

本轮该条件被正面触发，**从储备区取货**。4.11 那一行不删除，改标
「已于 2026-08 取货 → F110~F117」并保留原否掉理由 —— 那张表的表头写明
「登记不等于承诺，也不等于永久拒绝，边界变化时从这里取货」，取货应在原地留痕。

**产品定位随之扩张**：Mullion 不再只是「操作远端 tmux 的终端客户端」。隧道是
**可脱离终端窗口独立运行**的第二类对象。spec 的定位段要加这一句，否则将来
「隧道能不能在没开任何 pane 时活着」会反复被拿出来争。

参考实现是 PuTTY 的「连接 > SSH > 隧道」页（`/tmp/1.png`）。**但只参考字段集，
不参考模型**：PuTTY 里隧道是会话属性，本设计里隧道是一等对象（见 D1）。

## 决策

### D1 隧道是一等对象，引用会话，且**另开一条专用连接**

```
会话 web-01（已连）              隧道 #1（引用 web-01）
  └─ Arc<Handle> A                 └─ SshConnection B   ← 另一条 TCP
       ├─ pane 1 (PTY)                  └─ direct-tcpip
       └─ pane 2 (PTY)
```

这是**有意偏离两处既有约定**，两处都必须在新 ADR 里写明理由：

1. **偏离 PuTTY 模型**（隧道属于会话）。取一等对象是为了「不开终端窗口也能转发
   3306 给本地 DBeaver」。作为会话子配置就做不到这件事。
2. **偏离 ADR-009**（一条 SSH 连接承载多单元，明确否掉「每单元一条 TCP + 认证」）。
   ADR-009 的推理针对 **pane**：pane 数量随分屏增长且用户会频繁开关，每次都付一次
   完整建链不可接受。隧道的数量级和生命周期不同 —— 手动启停、长期驻留、通常个位数。

   **并且「另开连接」在类型层面反而是必需的**：`russh 0.54.5` 的
   `tcpip_forward` 签名是 `&mut self`（`client/mod.rs:696`），而
   `channel_open_direct_tcpip` 是 `&self`（`:649`）。会话的 handle 以
   `Arc<Handle<ClientHandler>>` 在多 pane 间共享，拿不到 `&mut` —— **复用会话连接
   的方案下 `-R` 编译不过**。隧道独占自己的 `SshConnection` 才有可变借用。

**建链复用 `establish()`**：`session.rs:136` 的 `establish(cfg, policy)` 已经包含
代理 → 跳板链 → 握手 → 指纹 → 认证全链路。隧道拨号 = 用被引用会话的参数构造
`SshConfig` 后调它，不重写任何拨号逻辑。

### D2 纯引用，不覆盖

隧道**不能**覆盖被引用会话的任何连接参数（不能「用 web-01 的地址但换个用户名」）。
要用不同身份 → 建一条新会话。

依据是 spec §C 已经拒绝过「引用 + 局部覆盖」的二义模型，理由是
「这条记录到底用哪个用户名永远需要现场推理」。

**推论：隧道没有自己的 `secrets.enc` 条目**，凭据全部活引用被引用会话那条。
这同时避开了 `vault.rs:78` 的 `secrets.retain(|k,_| live.contains(k))` —— 那个 GC
按活着的 `SessionId` 裁剪密文，隧道若自带密文条目会被它当孤儿清掉。

### D3 悬垂：删除前二次确认，删除后拒绝启动

跳板（`network.rs:46` 的 `JumpRef`）已有既定约定，测试名写死了：
`jump.rs:219 dangling_reference_is_rejected_never_degraded_to_direct`
—— **悬垂引用直接拒绝，绝不降级**。隧道沿用，不发明第二套。

但隧道要比跳板多一道确认，因为两者的**发现时机**不同：

| | 何时被使用 | 引用失效后 |
|---|---|---|
| 跳板 | 只在拨号那一刻 | 下次拨号立刻报错，用户当场知道 |
| 隧道 | 后台长期运行 | 静默停止，用户几小时后才在 DBeaver 里发现 |

因此删除会话时，若有隧道引用它：确认框列出受影响隧道（标出其中几条正在运行），
确认后允许删除。隧道**保留为悬垂状态并标红**，启动时拒绝。

**运行中的隧道必须立即停止**。一条指向已删除会话的端口继续在本机 listen，
是安全问题不是体验问题。

### D4 存储：`sessions.toml` 的 `[[tunnel]]`，schema v6 → v7

```toml
schema_version = 7

[[tunnel]]
id = 1
session_id = 7            # 引用；悬垂时保留原值，UI 标红
kind = "local"            # local | remote | dynamic
listen_port = 3306
local_only = true         # 见 D5
target_host = "db.internal"   # dynamic 时不写
target_port = 3306            # dynamic 时不写
note = "生产库"
autostart = false         # 保留字段，本期 UI 不出（见 D6）
```

**不新建 `tunnels.toml`**。理由：

- `vault.rs:1` 写死「唯一碰文件系统的地方」，且用 `write_atomic` 一次原子写。
  拆成两个文件就产生「sessions 写成功、tunnels 写失败」的部分成功状态。
- 隧道引用 `SessionId`。同文件天然保证引用完整性 —— 两个文件会出现
  「用户手动回滚了 sessions.toml，tunnels.toml 里的引用全悬垂」。

迁移：`migrate.rs` 现成的 v1→v6 链条接一节，v6 → v7 只需「无 `tunnel` 键 → 空数组」。
id 分配同 `SessionId`：现有 max + 1。

### D5 绑定安全：默认本机；`-L` 可放开，`-D` 锁死

默认 `127.0.0.1`。**不给自由文本框**填任意 bind 地址：真实场景 99% 只有
「仅本机」和「全网卡」两种，文本框只多引入「填了个不存在的网卡 IP、绑不上、
报错看不懂」这条失败模式。要绑特定网卡的需求出现了再加。

| 类型 | 放开到 `0.0.0.0` | 理由 |
|---|---|---|
| `-L` | **允许**，勾选时红字警告 | 暴露一个**特定目标**（`db:3306`），风险有界，有真实用途 |
| `-D` | **禁止**，勾选框 disabled 并写明理由 | 暴露**任意目标** |

`-D` 放开 = 把本机变成一个**无认证的开放 SOCKS5 代理**：局域网内任何人都能经它
访问远端主机能访问的一切内网资源，且流量在远端日志里全部记在**用户自己的账号**
头上。这不是「风险大一点」，是性质不同，所以用独立策略而非同一个开关。

**`-R` 的远端绑定另论**（D9）。

### D6 纯手动启停

隧道列表里点「启动 / 停止」。软件启动时一条不拉。数据模型留 `autostart` 字段，
本期 UI 不出这一项。

理由：D1 定了每条隧道启动 = 一次完整建链，可能要 TOFU 确认 / 输密码 / 输私钥口令。
自动启动意味着**开机瞬间并发拨 N 条 SSH、糊一屏模态框**，在高延迟代理链路下还全部超时。
手动启停保证所有交互都有明确的用户在场上下文。

F40~F44 的 `AutomationPrefs` 调度器**不能复用** —— 那是「会话连上之后在 PTY 里发命令」，
与隧道的「独立建链」不是一回事。

### D7 重连：有界指数退避

1s → 2s → 4s → … 封顶 30s，连续失败 8 次后停下标红等人工。

**这不违反 ADR-009 的「不做 per-unit 重连」**，因为那条推理不适用于隧道：

- **pane 断了不能重连**：滚动内容、正在跑的 TUI 状态都没了，重连回来是空 shell，
  语义不等价。
- **隧道是无状态的**：重连后转发语义**完全等价**，用户侧唯一感知是那一瞬间的 TCP
  连接断了、新连接又能用。

两条硬约束：

1. **自动重连只在无需交互时进行**。凭据没存（要现场输密码）或需要私钥口令 →
   停下等人，绝不后台反复弹窗。「能否自动重连」是每条隧道的**可计算属性**，
   不是全局开关。
2. **指纹变更立即停止、绝不重试**。指纹变了可能是中间人，自动重连等于自动把凭据
   往可疑主机上送。

### D8 三种转发的实现要点

按 `russh 0.54.5` 实际签名（已核对 `~/.cargo/registry/.../russh-0.54.5/src/client/mod.rs`）：

**`-L` 本地转发**（`tunnel.rs`）

本机 `TcpListener` → 每个入站连接调
`channel_open_direct_tcpip(&self, host: A, port: u32, originator_address: B, originator_port: u32) -> Result<Channel<Msg>>`（`:649`），
然后双向搬字节。

**`-R` 远程转发**（`tunnel.rs` + `session.rs` 的 `ClientHandler`）

`tcpip_forward(&mut self, address: A, port: u32) -> Result<u32>`（`:696`，返回服务端
实际分配的端口；请求 0 时用它拿真实端口）。服务端回连走
`Handler::server_channel_open_forwarded_tcpip(&mut self, channel, connected_address,
connected_port, originator_address, originator_port, session)`（`:1810`）。

**该回调的默认实现是 `async { Ok(()) }`，即把 `Channel` 直接丢弃** —— 这就是
ADR-009 不变量 3「channel 泄漏」的同类陷阱：`russh` 的 `Channel<Msg>` 不会自动发
CHANNEL_CLOSE。必须在回调里接管 channel 并交给转发任务，任何提前返回的路径都要
显式 `channel.close().await`。

停止隧道要调 `cancel_tcpip_forward(&self, address, port)`（`:722`），不能只丢连接。

**`-D` 动态转发**（`socks5_server.rs` + `tunnel.rs`）

本机 `TcpListener` 上实现 SOCKS5 **服务端**（RFC 1928），每个 `CONNECT` 翻成一次
`channel_open_direct_tcpip`。

`mullion-ssh/src/proxy.rs` 已经实现了同一份 RFC 的**客户端**（F4，`socks5_handshake`），
常量表、回复码表（`socks5_reply_reason`）、以及「用 `tokio::io::duplex` 喂假流」的
测试手法全部复用，不各写一套。

两条边界（技术事实，非决策）：

- **不做 UDP ASSOCIATE**，且做不到：SSH 的 `direct-tcpip` 只搬 TCP，SOCKS5 的 UDP
  转发在 SSH 上没有承载（除非上 `-w` tun 设备，那是另一个产品）。收到该命令直接回
  `0x07 命令不支持`。
- **只提供 `NO AUTH`**：D5 已把 `-D` 锁死在 `127.0.0.1`，能连上它的只有本机进程，
  加一层用户名密码挡不住任何东西，只增加配置面。

### D9 `-R` 的远端绑定：允许请求，但明写不可验证

`tcpip-forward` 请求带 bind_address，但 **sshd 默认 `GatewayPorts no` 会把它强制降级
成 `127.0.0.1` 且不报错**；协议响应只回端口号、不回实际绑定地址 —— 客户端
**结构性地无法验证**这件事是否生效。

所以给勾选框，但启动成功后在隧道详情里挂一行：

> ℹ 已请求绑定 `0.0.0.0`；实际是否生效取决于服务端 `GatewayPorts`，本客户端无法验证。

不假装知道结果（CLAUDE.md：「不要自己编一个看起来像通过了的结论」；spec F43 也拒绝过
「给用户错误的安全承诺」），也不因为验证不了就堆死能力。

### D10 分层：`TcpListener` 与 SOCKS5 服务端放 `mullion-ssh`

```
mullion-ssh/
  proxy.rs           SOCKS5 客户端（F4，已有）
  socks5_server.rs   SOCKS5 服务端（新，F113）
  tunnel.rs          TcpListener + 字节搬运 + 生命周期（新）
  session.rs         establish() / ClientHandler（已有，加 -R 回调）
```

依赖方向不变。三条理由：

1. `mullion-ssh` 的职责描述就是「**不认识『pane』『窗口』，只认字节流**」。隧道恰好
   只认字节流。
2. `SshConnection::handle()` 是 `pub(crate)`（`session.rs:107`）—— 隧道要拿 handle
   开 channel，**只有同 crate 才够得着**。放 app 就得把 handle 提成 `pub`，
   等于把「外部拿不到就不会误 Drop」那条保护拆掉。
3. 全部能脱离 GUI 纯测：起真的 `TcpListener` + 假的 channel 端，断言字节双向搬运正确。
   放 app 里这块逻辑只能靠人眼在 Windows 上验。

### D11 UI：会话管理器顶层模式切换

```
┌──────────────────────────────┐
│ ( 会话 )  【 隧道 】         │ ← 模式切换
├─────────┬────────────────────┤
│[搜索..] │ 类型：本地 (-L) ▼  │
│▶ 3306   │ 引用：web-01 ▼     │
│□ 1080   │ ── 本机侦听 ────    │
│         │ 端口：3306          │
│ + 新建  │ ☑ 仅本机可连        │
└─────────┴────────────────────┘
```

不新开窗口：复用 P1-a/P1-b 打磨过的窗口骨架（搜索框、删除二次确认、脏标记 /
关窗确认、Tab 角标三态）。独立窗口意味着这四套全部重写。

**左栏一级组织轴不变**（仍是 `group_manager::group_sessions` 归桶）。隧道模式下左栏
换成隧道列表，**不做分组、不做三档密度**（那是会话列表的 F61/F80 成果，隧道行结构不同）。

**协议筛选 chips 本期不做。** 拷问阶段（Q1）把「左栏分三段」改成了「协议筛选」，
但那个替代方案现在没有载体：`Protocol` 只有 `Ssh` / `Sftp` 两个值，而
`session_map.rs:42` 让 `Sftp` 直接返回 `SftpNotSupported` —— 库里所有会话实际都是
SSH。一个只有单一有效值的筛选器是纯噪音。**等 F50~F57 落地、库里真的存在两类会话时
再做**，届时单开编号。隧道不进这个筛选器（它不是 `Protocol` 的一个值，是另一类对象）。

### D12 字段标签随类型翻转

PuTTY 用一组固定标签表达三种方向，但语义在类型间是**反转**的：

| 类型 | 谁在侦听 | 谁去连 | 「目标主机」由谁解析 |
|---|---|---|---|
| `-L` | **本机** 3306 | **远端** 去连 `db:3306` | 远端主机 |
| `-R` | **远端** 8080 | **本机** 去连 `localhost:80` | 本机 |
| `-D` | **本机** 1080 | 目标由 SOCKS 客户端逐次指定 | —（无固定目标） |

填错的症状是「连上了但连不通」，且错误在远端，排查极难。而 `-D` 时那两个目标框
根本没有意义（PuTTY 里它们仍然亮着还预填 `localhost`，是纯误导）。

所以标签随类型改写，每类配一句「谁解析这个地址」，`-D` 时目标区**整块消失**。
底层存储字段名不变（`target_host` / `target_port`），只有 UI 措辞变。

### D13 常驻状态：状态栏指示器 + 失败 toast

状态栏右侧 `right_to_left` 区插在 `automation` 之后、`"UTF-8"` 之前
（`chrome.rs:125-165`）。按**最坏状态**三态上色：

| 状态 | 文案 | 色 |
|---|---|---|
| 全部运行 | `隧道 2/2` | `fg_muted` |
| 有重连中 | `隧道 1/2 ↻` | `warn` |
| 有失败停止 | `隧道 1/2 ✗` | `danger` |

`N` = 运行中，`M` = 已配置总数。点击跳到会话管理器隧道模式，悬停出 tooltip 列明细。

选状态栏是因为 `chrome.rs:112` 已经把它的定位写死了 ——「**状态栏常驻，不受那两个
弹窗开关状态影响，兜底展示**」，正是隧道需要的语义。

**只改颜色不够**：一条隧道从「运行中」掉到「重连中」时，用户正盯着 DBeaver 报错，
不会去看状态栏。所以**状态跃迁到失败态时弹一次 toast**（`toast.rs` 已有机制）。

## 不做什么

| 条目 | 理由 |
|---|---|
| X11 转发 | spec §4.11 同一行登记，本次只取隧道那一半 |
| 隧道自动启动 | D6；字段留了，UI 不出 |
| 隧道分组 / 三档密度 | D11；会话列表的成果不硬套到结构不同的隧道行上 |
| 覆盖被引用会话的参数 | D2，spec §C 已拒绝二义模型 |
| SOCKS5 UDP ASSOCIATE / 认证 | D8，一个做不到、一个挡不住任何东西 |
| 自由填 bind 地址 | D5，只多一条失败模式 |
| 协议筛选 chips | D11，`Sftp` 未实现前只有单一有效值，等 F50~F57 |
| SFTP | **本设计完全不含 SFTP**。现状 `Protocol::Sftp` 在模型里但 `session_map.rs:42` 直接返回 `SftpNotSupported`，归 F50~F57 / v0.4 |

## 测试

**`mullion-store`（纯单测）**

- `v6 → v7` 迁移：无 `tunnel` 键 → 空数组；已有字段一个不动
- 隧道 id 分配 max+1；与 `SessionId` 独立编号
- 悬垂检测：`session_id` 指向不存在的会话 → 报错而非降级（对齐 `jump.rs:219` 的命名）
- 删除会话时能查出受影响隧道列表（含运行态由 app 侧合并）
- `secrets.retain` 的 GC 不受 `[[tunnel]]` 影响（隧道无密文条目）

**`mullion-ssh`（纯单测 + 真 TcpListener，无需 GPU/远端）**

- `-L`：起真 `TcpListener` + 假 channel 端，断言双向字节搬运正确、连接关闭双向传播
- SOCKS5 服务端：`duplex` 喂假客户端，覆盖三种 ATYP、`UDP ASSOCIATE → 0x07`、
  非 5 版本字节 → 拒绝、认证方法协商只回 `NO AUTH`
- **channel 不泄漏**：`-R` 回调里任何提前返回路径都 `close()`（对齐 ADR-009 不变量 3）
- 退避序列是纯函数：1/2/4/…/30 封顶、8 次后停
- 指纹变更 → 立即停且**不进重试队列**（这条要能自证变红）

**`mullion-app`（egui 无头）**

- 模式切换后左栏渲染的是隧道列表而非会话列表
- `-D` 选中时「仅本机可连」勾选框 disabled、目标区不渲染
- 标签随类型翻转：`-L`/`-R` 下「转发到」的副文本不同
- 状态栏三态取**最坏**状态，不是取第一条
- 删除会话确认框列出受影响隧道
