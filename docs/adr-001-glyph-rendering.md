# ADR-001: 字形渲染选型 —— v0.1 先用 glyphon

- 状态: 已接受
- 日期: 2026-07-23
- 关联: spec.md Q1、N2、N3、F16;风险 R1、R5

## 背景

终端渲染有两个独立难点:

1. **字形整形 + 字体回退**:CJK 宽字符占两格、缺字回退、emoji/ligature(对应 F16)。
2. **高吞吐网格绘制**:流式输出时每帧上千个单元格(对应 N2/N3)。

需要在「省事、可维护」与「性能上限」之间选一条渲染路径,且受两条风险约束:
依赖 crate API 漂移(R1)、单人维护范围易失控(R5)。

## 决策

v0.1 使用 **glyphon**(cosmic-text 整形 + wgpu 字形图集)。
渲染逻辑封装在一个窄接口后面(概念上 `draw(grid, damage, surface)`),
glyphon 只是该接口的一个实现。

## 备选与否决理由

**等宽网格专用 wgpu pipeline**(每单元格一个 instanced quad + 自建字形图集,
Alacritty / WezTerm 的路线)。性能上限更高,但:

- 要自己实现字体回退 / CJK / 缺字处理,工作量以「月」计,与 R5 正面冲突;
  glyphon 直接免费提供这块(README 估算「省 2 个月」)。
- N2/N3 达标主要靠 T2 攒帧 + T3 帧率封顶 + F12 damage 差分渲染这套「少画帧」策略,
  而**不是**靠 per-cell 绘制的极致速度。瓶颈更可能在「画多少帧」而非「每帧多快」。

故现在不选;保留为未来的替换实现。

## 后果 / 权衡

- glyphon 0.7 与 wgpu 23 版本强绑定,升级容易打架(R1)。**锁死版本,升级单独开 PR。**
- 渲染接口保证 `mullion-app` 上层不依赖具体渲染器,未来替换不动上层。

## 重新考虑的触发条件

当 N2/N3 埋点数据显示瓶颈**落在文本布局 / 整形**(而非提交帧数)时,
替换为等宽网格专用 wgpu pipeline —— 接口不变,只换实现。在拿到这个数据之前不换。
