# 实机采集与验收运行手册

> 性能类切片（F157~F180、N1/N5）几乎每一轮都以「待人工验」「等实机日志回来再定」
> 结束。这份手册是那个回收动作的固定流程。
>
> **2026-08-28 重写。** 初版设计了三趟带编排的手工测试（静置 A/B、压力剧本、
> 七项目视）。第一次实跑证明**其中两趟不需要**：日志自陈能力比预期强得多，
> 一份「正常使用 34 分钟」的日志就回答了三个待定问题里的两个半。
> 编排掉了，判读方法留下了。

## 采集：一步

| 项 | 值 |
|---|---|
| 动作 | 正常用 mullion 工作 → 菜单「配置 → 导出脱敏日志…」 |
| 落点 | `%APPDATA%\mullion\config\mullion-redacted-<实例id>.log`（toast 会显示完整路径） |
| 前提 | 在**已经跑了一段时间**的窗口里点。刚启动的实例日志里什么都没有 |

**不需要编排静置段。** `is_idle()` 为真的 5 秒窗口一行都不写，写盘的每个窗口
由 `profile.load` 的 `scene=` 自动打好标签。你去开会吃饭的那些时段就是静置样本。

**不需要跑压力剧本。** 你正常用满 8 pane 的日子比编出来的剧本真实，
F177 预算闸超了会自己喊。

**一个已知坑（F180 修好之前）**：脱敏器把 `-` 当成主机名。日志里的
`wev=host#N` / `dirty=host#N` / `@host#N/6`，原文都是 `-`（空表占位符）。
判读时先在心里还原回来，别去找那台不存在的机器。

## 判读：三段脚本

日志按 5 秒窗口聚合，一个窗口五行（概览 / `load` / `cpu` / `mem` / `gpu`）+
可选的 `profile.pane`。按秒级时间戳把它们配对，然后：

### ① 白跑帧（F178 的基线）

筛 `scene=ui-only` 的窗口，看 `present=0` 那些——画了几十帧、一帧都没提交 GPU：

```
frame present wake sched evt  wev
   39       0    90    55  37  cursor:36     ← 36 个真实事件 → 39 帧 → 0 提交
  170      27   431   270 165  cursor:153    ← 浪费 84%，主线程 CPU 4%
```

**看三个比值**：
- `frame : wev 总数` —— 放大倍数（基线 ≈ 1:2.5）
- `sched : evt` —— **大于 1 就是自激**（多出来的那一半是 egui 的 `repaint_delay=ZERO` 转回来的）
- `present : frame` —— 浪费率

`curdup=` **不是**用来看「事件多不多」的，是用来分辨**幽灵事件 vs 真实事件**的：
坐标 bit 相等 → 可以按位置掐；坐标在变 → 事件是真的，只能掐放大链。
2026-08-28 实测 286/286 个窗口 `curdup=0`，**幽灵假设已证伪，别再往那个方向查**。

### ② N1 / N5

- **N5**：`profile.mem` 的 `ws=`，与任务管理器进程页「内存」列同口径。
  别看 `commit=`（两者差着 100MB，实测 226 vs 323）。超了 F177 会写
  `WARN profile.mem.over`。
- **N1**：**目前读不出来**（F179）。`total=` 归一后取整，16 核机上一档 6.25% 单核，
  N1 的 1% 整个落在一档内，**永远显示 0%**。别把 `total=0%` 当达标证据，
  也别拿「窗口没写盘」当证据——空闲门的阈值（`IDLE_CPU_PCT=5` 归一 = 0.8 个核）
  比 N1 松一个量级。能看的只有不归一的 `main=`，且分辨率同样勉强。

### ③ 优化是否回本

| 段 | 健康值（2026-08-28 v0.1.78 实测） | 读法 |
|---|---|---|
| `reshape=hit:N/miss:N` | hit:14469 / miss:51（99.6%） | 掉下来说明 F174 的内容寻址失效 |
| `bands=脏/总` | 50 / 990（跳过 95%） | `0/N` 是**好结果**（全带命中），不是「没统计」 |
| `text_prepare` | p50 段 p95=2.0ms，最坏窗口 max=16.4ms | 回到 60ms 量级说明整形或分带退化 |
| `fp=hit:N/miss:N` | 内容真在变时几乎全 miss，静止时全 hit | 判据写错导致永远 miss 时**画面完全正确、日志一切正常**，只有这个比值会掉 |
| `profile.gpu` 的 `backend=` | Vulkan（Windows 上 wgpu 默认不选 DX12） | 先确认它再读后面的数字 |

## 仍然只有人眼能判的一件事

**屏幕上有没有留着陈旧字形**（F172 带指纹漏项 / F174 空行合并）。这两类
**不报错、不 panic、测试全绿**。

现有手段：把日志详细度切到 **Debug** 会打开 F172 影子校验（从结果侧独立推一遍
每个字形的 `glyph_id/x/y/color`，与输入侧指纹互为独立证人），然后

```
grep "F172 影子校验失配" mullion-redacted.log
```

**但 Debug 档每帧全带都算，太贵，不能常开**——而且那个档下测出来的
`text_prepare`／帧数／CPU% 量的是加了校验的版本，不是发布形态。
所以它只能当「怀疑画面有问题时开一趟」的排查手段，不是常态守护。

想把这件事彻底机械化，需要把影子校验改成常开抽样（每 2 秒抽一帧付代价，
非采样帧里带脏时把 `slot.shadow` 置 `None` 作废以避免假阳性）。
**尚未实施**，需要时开一条 F 编号。

## 交回什么

1. `mullion-redacted-<id>.log`
2. 这台机器是**核显还是独显**——UMA 核显上 GPU 的每一份分配都计入进程私有
   工作集，N5 的 300MB 在两类机器上量的不是同一个东西
3. 一句主观判断：**用着卡不卡、闪不闪**。这一条没有任何日志能替代，
   而它恰恰是项目存在的理由（G1）
