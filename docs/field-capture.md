# 实机采集与验收运行手册

> 性能类切片（F157~F177、N1/N5）几乎每一轮都以「待人工验」「等实机日志回来再定」
> 结束。这份手册是那个回收动作的固定流程：**在 Windows 真机上跑一趟，把日志与目视
> 结果带回来**，让下一轮修法建立在数据上，而不是建立在直觉上。
>
> 无头容器里验不了的清单见 `CLAUDE.md`「你无法验证的东西」。

---

## 0. 前置

| 项 | 值 |
|---|---|
| exe | GitHub Release 的 `mullion.exe`（当前 v0.1.78） |
| 日志 | `%APPDATA%\mullion\config\mullion-<实例id>.log`（一实例一文件，F166） |
| 详细度 | 菜单「配置 → 设置 → 诊断 → 日志详细度」，或环境变量 `MULLION_LOG=debug` |
| 交回 | 菜单「配置 → 导出脱敏日志…」→ `mullion-redacted.log` |

**脱敏是尽力而为的模式匹配，不是「导出即安全」**——发出去前自己扫一眼有没有漏网的
主机名/IP/路径。

### 两个档位必须分两趟跑，不能合并

- **Info 档**用来**测量**。这是用户实际跑的形态，数字才有意义。
- **Debug 档**会打开 F172 影子校验（`text.rs:782`，从结果侧再推一遍带摘要来对账）。
  它**每帧都要多算一遍**——在 Debug 档下测出来的 `text_prepare`、帧数、CPU%
  **量的是加了校验的版本，不是发布形态**。Debug 档只用来查「有没有画错字」。

### 静置态的基线：日志里本来就不该是全空

`Snapshot::is_idle()` 为真的 5 秒窗口**一行都不写**（`render_line` 返回 `None`）。
所以静置采样的读法是反过来的：

> **静置 2 分钟（24 个窗口）里，profile 行越少越好；一行都没有 = 最好的结果。**

但预期**不是零**。已知的合法噪声源：

- 远端 tmux 状态条刷新会持续送零星字节 → `inbound_bytes != 0` → 破空闲门。
  这类窗口的 `profile.load` 场景标签应是 `unattributed` 或 `ui-only`，
  **不该是** `remote-output`（速率阈值 `REMOTE_OUTPUT_BPS` 就是为了滤掉涓流）。
- 远端状态自举没配成时每 30 秒重试一次（`docs/remote-state-setup.md`）。

判据是**比例和段内数字**，不是「有没有行」。

## 1. 本轮（v0.1.78）要回答的三个问题

这一轮欠的账横跨 v0.1.73~v0.1.78 五个版本，按重要性排：

| # | 问题 | 谁在等它 | 答不出的后果 |
|---|---|---|---|
| Q1 | 空闲时的自发窗口事件源是什么？还在吗？ | **F171**（当初明写「只加埋点不改行为，判据等实机日志回来再定」） | 下一步只能猜，而已知的直觉修法**是错的**——只掐调度那一半会让帧数从 149 涨到 160，因为帧闸此刻正在吸收自激 |
| Q2 | N1（空闲 CPU < 1%）与 N5（8 pane + 10000 行 < 300MB）达标了吗？ | **里程碑 v0.3 的判定条件** | 性能主线永远无法宣布收口 |
| Q3 | F172 分带 / F174 空行合并有没有在屏幕上留下陈旧字形？ | F172 的 `trim` 契约、F174 的内容寻址 | 这两类**不报错、不 panic、测试全绿**，只有人眼能判，已经在真机上跑了几天 |

## 2. 趟 1 —— 静置 A/B（Info 档，回答 Q1 + N1）

A 与 B 的**唯一差别是鼠标指针在不在窗口内**。这个对照直接指认 F171 当初锁定的
首要嫌疑：**幽灵 `CursorMoved`**。

1. 设置里确认日志详细度 = **Info**（默认档）。
2. 连上 8 个 pane（分屏 + 标签皆可），各滚出一些回溯，让它进入常态。
3. **静置 A**：鼠标指针**停在窗口内**（比如终端网格中央），
   **不碰键鼠 2 分钟**。手表计时，中途不要碰。
4. **静置 B**：把指针**移到窗口外**（另一个显示器 / 任务栏上方），
   同样**不碰键鼠 2 分钟**。
5. 导出脱敏日志。

### 怎么读

```
grep profile mullion-redacted.log
```

关键段（概览行）：

| 段 | 含义 | 想看到 |
|---|---|---|
| `wev=` | 按 winit 事件类型分桶的计数（F171），只统计 egui 说了 `repaint:true` 的那些 | A 段里哪个类型占大头。`CursorMoved` 一枝独秀 = 嫌疑坐实 |
| `curdup=` | 其中坐标与上一次**逐 bit 相等**的比例 | 高比例 = 事件是幽灵的，可以按坐标去重 |
| `wake=Nx/rr=sched:N,evt:N` | 唤醒次数与来源拆分 | evt 与 sched 的比例 |
| `frame=Nx present=N` | 过了帧闸的帧数 / 真正提交 GPU 的帧数 | `present` 远小于 `frame` = 整帧指纹在挡，自激还在 |
| `profile.cpu` 的 `cpu=` / 主线程 CPU% | N1 的直接读数 | **< 1%** |

**A 与 B 的差值才是结论**，单看一边说明不了什么。三种可能的形态：

- **A 有行、B 几乎没有** → 事件源与指针位置绑定，`CursorMoved` 坐实，
  下一轮做「按 bit 相等去重」。
- **A/B 都有、`wev=` 分布相同** → 与指针无关，得换嫌疑（当初已排除
  `AxisMotion`/`Occluded`/`Resized`/`Moved`/`Focused`/IME ledger/present 回声，
  记录在 `slice-f171` 那一轮）。
- **A/B 都近乎无行** → **自激已被 F158/F172/F174 顺带修掉**，F171 这条线
  直接收口，N1 达标盖章。（这是有先例的：v0.1.66 曾见空闲 CPU 3.5%，
  0.1.76 后疑已 ≤0.2%，就差这一次核实。）

## 3. 趟 2 —— 画面正确性（Debug 档，回答 Q3）

**这一趟不看任何性能数字。** 只回答「屏幕上有没有留着不该在那儿的字」。

设置里把详细度切到 **Debug**，然后逐项做完、**每项做完立刻看一眼屏幕**：

| # | 动作 | 盯什么 | 为什么这一项能杀死它 |
|---|---|---|---|
| 1 | 拖分屏分界线，来回拖 | 被拖动那侧的文字有没有留在旧位置 / 重影 | 顶点里**烤着绝对坐标**，整形却全命中（F172 的三类漏网之一） |
| 2 | 切标签，来回切 | 新标签上有没有闪出上一个标签的字 | 带指纹跨标签 |
| 3 | 换字号、换字体 | 有没有一部分行是旧字号 | 全带应当同时脏 → 触发 `trim` |
| 4 | 换主题 | 有没有一块保持旧配色 | `default_color` 变而行内容没动（F172 三类漏网之二） |
| 5 | 打中文（组字中途停住看候选） | 拼音串位置对不对，退出组字后有无残留 | preedit 走临时 buffer，不进整形缓存（三类漏网之三） |
| 6 | 滚回历史再滚回来，快速滚 | 有没有整行整块的陈旧字 / 空行位置错 | **F174 内容寻址后空行全窗口共用一条**，这是新引入的合并 |
| 7 | 跑满屏 TUI（真跑一次 Claude Code） | 整体有没有花屏 | 综合 |

同时在日志里搜：

```
grep -n "F172 影子校验失配" mullion-redacted.log
```

**一条都不该有。** 有 = 从结果侧独立推出来的带摘要与输入侧指纹对不上，
F172 的 `trim` 契约破了，那一带正在画别的字形。

## 4. 趟 3 —— 压力与 N5（Info 档，回答 Q2 剩下一半）

切回 **Info** 档。

1. 8 个 pane 全部连上，**每个 pane 都滚出满 10000 行回溯**
   （`for i in $(seq 1 12000); do echo "line $i ................"; done`）。
2. 静置 30 秒让内存稳下来，记一次读数。
3. `cat` 一个几十 MB 的文件（大输出吞吐 + `text_prepare` 尖峰）。
4. 大范围滚动回溯，快速上下。
5. 再静置 30 秒，记第二次读数。
6. 顺手把任务管理器里该进程的「内存」列拍下来。

### 怎么读

```
grep "profile.mem\|profile.load\|profile.gpu" mullion-redacted.log
```

| 读数 | 判据 |
|---|---|
| `profile.mem` 的 `ws=`（专用工作集） | **对得上任务管理器那一列**。这是 F176 双口径的意义所在——上一轮 289 对不上 428 才被迫上 VMMap |
| `profile.mem` 的 `commit=` | 提交量，减法算在它上面（工作集会被系统裁剪，最小化窗口时尤甚） |
| `ws` 是否 < 300MB | **N5 达标判据**。注意 UMA 核显机器上 GPU 每一份分配都计入进程私有工作集，独显机器量的不是同一个东西 |
| `profile.mem.over ws=…MB > N5 300MB` | **F177 预算闸**。超了它应当自己喊出来。这一轮顺带验证「它到底出不出声」 |
| `profile.load` 的 `scroll/xfer/key/in` | 场景分母，用来判断某个窗口的数字该不该那么大 |
| `text_prepare` 的 `p50/p95/max` | F174 之后滚动时的尖峰是否消失（改之前 `p95=16.4ms/max=65.5ms`） |
| `reshape=hit:N/miss:N` | 滚动时 miss 应当只有新露出的那几行，不再整块 pane 全 miss |
| `egui_feed=` | F175 新埋点，被 `window_event=` 段**包含**，两者相减 = 路由判定+标脏的开销 |
| `bands=脏/总` | `0/N` 是**好结果**（全带命中），不是「没统计」 |
| `profile.gpu` 的 `backend=` | 先确认是 Vulkan 还是 DX12 再读后面的数字。**Windows 上 wgpu 默认选 Vulkan 不是 DX12** |

## 5. 交回什么

1. `mullion-redacted.log`（三趟可以是同一个文件，趟与趟之间隔开即可）。
2. 趟 2 那张七项表，每项写「正常 / 异常 + 一句现象」。
3. 任务管理器的内存读数（一个数字即可），以及**这台机器是核显还是独显**。
4. 一句主观判断：**现在用着卡不卡、闪不闪**——这一条没有任何日志能替代，
   而它恰恰是项目存在的理由（G1）。
